Part 1 · covers the four ways to move and transform data. Figure a4a: one input (files landing in gs://tw-lake-prod-landing, constructed) and four routes into BigQuery: scheduled SQL inside BigQuery ("Scheduled queries use features of BigQuery Data Transfer Service"), Dataflow running Apache Beam ("unified stream and batch data processing at scale"), Managed Service for Apache Spark (formerly Dataproc) clusters or serverless, a Cloud Run function per file. Each route tagged with its meter (bytes read or slot-hours; vCPU + memory time, per second per job; cluster or serverless time; requests + seconds). Yellow = scheduled SQL as the default when data is already in BigQuery.
Part 2 · covers events with Pub/Sub. Figure a4b: publisher -> topic -> subscriptions (pull, push, BigQuery subscription); "at-least-once delivery with no ordering guarantees" by default; exactly-once only on pull, same region. Card: why a pipeline must be idempotent (derived: at-least-once means duplicates possible). Link learn-streaming-data for streaming design.
Part 3 · covers choosing by workload. Figure a4c: decision tree: data already in BigQuery and SQL is enough -> scheduled SQL; per-file light work on arrival -> Cloud Run function; existing Spark code or libraries -> Managed Spark; streaming or complex batch with windows -> Dataflow. Cards: Cloud Run limits (request timeout default 5 min up to 60 min; jobs default 10 min up to 168 hours); Composer named only ("evolving to become Managed Service for Apache Airflow"; orchestration lives in learn-data-orchestration). Note the 5-minute scheduled query minimum is reported, not on the page: do not state it as Google's rule.
Real world: constructed "the Spark cluster that ran one SQL statement a day".
