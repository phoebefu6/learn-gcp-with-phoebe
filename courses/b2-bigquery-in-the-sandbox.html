Part 1 · covers what the sandbox is and its limits

A project with a fence instead of a card

5 min live

Google's sandbox page puts it plainly: you can use BigQuery "without providing a credit card or creating a billing account for your project". What you get in exchange is a fence. Queries get "the same free compute limit as the BigQuery free tier of 1 TiB of processed query data each month". Storage is a "lifetime limit of 10 GiB". Tables, views and partitions "automatically expire after 60 days". Streaming data, DML statements and the BigQuery Data Transfer Service are not supported. The public datasets, in the project bigquery-public-data, sit outside the fence and are free to read into.

LiveSetting it up3 min▶

Sign in to the Google Cloud console with any Google account and open BigQuery. If you have never attached a billing account, the console creates or picks a project for you and shows a sandbox banner at the top of the BigQuery page. That banner is your proof: there is no card behind this project, so there is nothing to overspend. You will not be asked for payment details at any point tonight.

In the Explorer panel, add the public project by name, bigquery-public-data, and open chicago_taxi_trips, then taxi_trips. The Schema tab shows the 23 columns you met in session 1; the Details tab shows the table's size. You are looking at the same rows as your 18,362-trip sample, at full size.

Self-studyWhat a "lifetime" 10 GiB means for a class2 min▶

The sandbox page says: "You are granted a lifetime limit of 10 GiB of storage. This quota is not refunded upon data deletion." Read that twice if you teach. A student who copies the whole taxi table into their own dataset to "have their own copy" will not fit, and a student who loads and deletes a few test tables has spent that storage for good. The professional habit follows: query public data in place, write only small result tables, and let the 60-day expiry clear them. When someone genuinely needs more, that is the moment to move to a billing-enabled project, not to work around the fence.

Real world

The workshop that ran out of storage on day two. A trainer asks every participant to load a few gigabytes of sample data into the sandbox, then delete it and load a cleaner version the next morning. The second load fails for half the room, because the deleted gigabytes still count. The story is a constructed composite; the rule behind it is Google's own wording, quoted above.

Part 2 · covers the first query and reading bytes before running

Read the bytes before you press Run

5 min live

BigQuery on demand is charged by bytes processed, and BigQuery's storage is columnar: "You're charged according to the total data processed in the columns you select". So the price of a query is decided by the columns it names and the rows it must scan, and both are known before anything runs. The console's query validator shows an estimate as you type; the bq tool's dry run returns the same kind of figure. Google calls that estimate "an upper bound". Tonight's query names three of the table's 23 columns.

LiveThe dry run, from the command line3 min▶

A dry run validates the query and reports the bytes it would process, without running it and without charge. In the console, the validator does this as you type. From a terminal with the Google Cloud CLI installed, the same check is bq query --dry_run --use_legacy_sql=false '...'. Make it a reflex before any query on a table you have not measured.

Notice what the estimate is built from: the columns you named and the rows the table must scan. The WHERE on the year filters rows out of the result, but on an unpartitioned table every row of those three columns is still read. Session 3 is where a filter starts to cut bytes, through partitions. For a feel of the size: the bench in session 8 models a three-column query over the full 211,670,894 rows at 4.58 GiB; it reads pickup_community_area where tonight's query reads payment_type, so treat it as the same order, not the same number.

Self-studyWhere the estimate can mislead you2 min▶

Three cases worth knowing. First, the estimate "is an upper bound": on clustered tables BigQuery only learns how many blocks it can skip while the query runs, so the real figure can be lower. Second, dry runs return 0 bytes on tables with row-level security, so a zero there means "not estimated", not "free". Third, LIMIT does not help: "applying a LIMIT clause to a query doesn't affect the amount of data that is read." Only fewer columns or fewer partitions do. The byte count itself follows BigQuery's documented logical sizes per data type (8 bytes for an INT64 or FLOAT64, 2 bytes plus the length for a STRING), not the compressed size on disk.

Real world

The SELECT * ... LIMIT 10 preview. An analyst new to BigQuery "peeks" at a large table with SELECT * LIMIT 10, expecting a tiny read, and burns a noticeable slice of the month's free terabyte on one look. The table's Preview tab would have shown the same rows without a query. The story is a constructed composite; the LIMIT rule is Google's.

Part 3 · covers putting a ceiling on a query

A ceiling on every query

5 min live

Reading the estimate is a habit; a ceiling is a guarantee. The query setting maximum_bytes_billed tells BigQuery the most a query may bill. If the query would bill more, Google's cost page says "the query fails without incurring a charge". It is the cheapest insurance in BigQuery, and it costs nothing to set in the sandbox, where it protects your free terabyte.

LiveSet it in the console or on the command line3 min▶

In the console, the query settings carry a Maximum bytes billed field. On the command line, pass --maximum_bytes_billed=1000000000 to bq query. A billion bytes is a constructed teaching value: large enough for tonight's three-column query on a partitioned table, small enough to stop a SELECT * on the full taxi table. Pick yours from your own dry runs.

One trap from Google's estimate page: for clustered tables the pre-run estimate is an upper bound, so a query can fail against the ceiling even though the bytes it would actually have read fit under it. When that happens, raise the ceiling for that query on purpose, rather than removing it.

Self-studyCustom quotas: the project-wide version2 min▶

A per-query ceiling protects against one bad query. A custom quota protects against a bad day. BigQuery has two: QueryUsagePerDay for the whole project, whose default is "200 Tebibytes (TiB) of data processed per project per day", and QueryUsagePerUserPerDay, unlimited by default. Google warns that when the project quota is hit, "BigQuery stops working for everyone in that project" until it resets, so the per-user quota is usually the kinder lever. Leader session 5, The bytes behind the bill, puts both next to budgets and spend caps.

Real world

The dashboard that refreshed every minute. A team wires a dashboard to an unpartitioned table and sets it to refresh every minute. Nothing breaks, so nobody looks, until the month's bill. A ceiling on the dashboard's service account would have turned the first expensive refresh into a visible error. The story is a constructed composite.

Check yourself

Three questions

Clear all three and builder session 2 gets stamped in your passport.

1 · A student loads 6 GiB into the sandbox, deletes it, and tries to load 6 GiB again. What happens?

The sandbox page says the 10 GiB storage limit is lifetime and "not refunded upon data deletion". Query public data in place and keep your own tables small.

2 · A query's estimate is above the maximum bytes billed you set. What happens?

Google's cost page: if the query would bill more than the setting, "the query fails without incurring a charge". Nothing is read and nothing is billed.

3 · Why is a dry run's estimate called an upper bound, especially for clustered tables?

The block pruning happens at run time, so the estimate assumes the worst. A side effect: a ceiling can refuse a clustered-table query whose actual read would have fitted.
