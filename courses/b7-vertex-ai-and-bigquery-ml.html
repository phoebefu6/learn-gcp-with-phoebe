Part 1 · covers BigQuery ML: models in SQL

Three statements, and the data stays put

5 min live

BigQuery ML is a set of SQL statements and functions. CREATE MODEL trains a model from a query's result and stores it in a dataset. ML.EVALUATE "lets you evaluate model metrics". ML.PREDICT is the function "you can use to predict outcomes by using a model". All three run where the table lives, so there is no export, no copy on someone's laptop, and the model is stored in a dataset you already govern.

LiveReading a CREATE MODEL3 min▶

The statement comes in three forms, CREATE MODEL, CREATE MODEL IF NOT EXISTS and CREATE OR REPLACE MODEL, followed by OPTIONS(...), where MODEL_TYPE is required, an optional TRANSFORM, and AS with the query that supplies the training rows. The label is the column you name in input_label_cols; every other selected column becomes a feature.

The MODEL_TYPE list on the CREATE MODEL page is long: linear and logistic regression (LINEAR_REG, LOGISTIC_REG), boosted trees and random forests, DNNs, AutoML, KMEANS for clustering, MATRIX_FACTORIZATION, PCA, AUTOENCODER, the time-series family ARIMA_PLUS and ARIMA_PLUS_XREG, CONTRIBUTION_ANALYSIS, and imported TENSORFLOW, TENSORFLOW_LITE, ONNX and XGBOOST models. Tonight's build-along uses the simplest, LINEAR_REG.

Self-studyWhat a model costs, and which edition has it2 min▶

BigQuery's pricing page treats the steps differently. "BigQuery ML jobs that perform inspection, evaluation, and prediction operations incur the same charges as on-demand query jobs": $6.25 per TiB, inside the same 1 TiB free each month. Training is separate: "Because CREATE MODEL queries incur different charges, you must calculate CREATE MODEL job costs independently". On demand, the row for built-in models (linear, logistic, k-means, PCA, time series, contribution analysis) shows "$312.50 / 1 tebibyte", fifty times the query rate. Our read of that table came from the page's raw HTML, so confirm which model types sit on that row before you budget. Prices: us-central1, BigQuery pricing page, 3 November 2026; re-verify.

On capacity pricing, editions decide access: "BigQuery ML is available in Enterprise and Enterprise Plus Editions", and the editions page lists Standard with "No access to BigQuery ML." One more line worth knowing before you train anything large: "The CREATE MODEL statement stops at 50 iterations for iterative models."

Real world

The churn model that never left the warehouse. An analyst at Tidewater (constructed) needs a first churn score for loyalty members. The old route is an export to a notebook, a copy of personal data on a laptop, and a review nobody wanted. The new route is a CREATE MODEL in the same project as the data, read by the same people who can already read the table. The model is simple; what it saves is the copy.

Part 2 · covers the sandbox question, honestly

What the sandbox page says, and what it does not

5 min live

The builder track runs on the BigQuery sandbox, so the obvious question is whether CREATE MODEL runs there. The honest answer, as of 3 November 2026, is that neither the sandbox page nor the pricing page says. BigQuery ML is not on the sandbox page's list of unsupported features, and it is not mentioned anywhere else on that page. An absence is not a rule either way, so these pages do not resolve it: you test it in your own console.

LiveHow to treat an undocumented answer3 min▶

Three things are documented and you can rely on them. The sandbox runs "without providing a credit card or creating a billing account for your project", with "a lifetime limit of 10 GiB of storage" and "the same free compute limit as the BigQuery free tier of 1 TiB of processed query data each month", and tables "automatically expire after 60 days". Its unsupported list is "Streaming data", "Data manipulation language (DML) statements" and "BigQuery Data Transfer Service". And BigQuery ML's pricing is on the pricing page.

What is not documented is the link between them. So the build-along labels every CREATE MODEL box "needs a billing-enabled project, confirm in your own console". Run step 2 in your sandbox. If it runs, write down the date: a free product's limits can change without notice. If it is refused, the same SQL runs unchanged on a billing-enabled project. Either result is yours, from your console, not a claim on these pages.

Self-studyWhy the sandbox's storage limit matters for models2 min▶

A model is stored in a dataset, next to tables. In the sandbox, storage has a lifetime ceiling, and "This quota is not refunded upon data deletion." So if your sandbox does accept training, small experiments are cheap and large ones spend an allowance you cannot get back. The pricing page's free-tier table says "BigQuery ML models and training data stored in BigQuery are included in the BigQuery storage free tier", so a stored model counts as storage like any table; how its size is measured is not stated there, so keep sandbox models small.

The same caution applies to the training query itself: in the sandbox it would draw on the 1 TiB a month, and a CREATE MODEL over a full public table can read a lot of it. Dry-run the AS SELECT part on its own first, exactly as in session 2.

Real world

Two analysts, two answers. Mei says BigQuery ML works in the sandbox; a colleague says it does not (constructed). Both are reporting what their console did, on different days, and neither wrote the date down. The team's wiki now says "tested on DATE, result X, see the sandbox page" instead of a rule nobody can trace. That is the habit this Part teaches: when the documentation is silent, record evidence, not opinion.

Part 3 · covers Vertex AI (now Gemini Enterprise Agent Platform) as the platform

The platform beyond SQL, under its new name

5 min live

When a model needs custom code, its own training job, a managed endpoint, or a third-party foundation model, the work moves from BigQuery to Google's ML platform. Most people still call it Vertex AI. Since 22 April 2026 Google calls it Gemini Enterprise Agent Platform, Agent Platform for short, and almost every component was renamed with it. Knowing both names is now part of reading any Google Cloud ML material.

LiveFour parts a data team actually opens3 min▶

Model Garden "is an AI/ML model library that helps you discover, test, customize, and deploy models and assets from Google and Google partners." Third-party models live here, Claude among them: "To access a Claude on Google Cloud model, go to its Model Garden model card." How to call Claude there is the subject of learn-claude, session 68; these pages cover the platform only.

Workbench instances "are Jupyter notebook-based development environments", the place for code that SQL cannot hold. Pipelines "lets you automate, monitor, and govern your machine learning (ML) systems in a serverless manner." Model Registry "is a central repository where you can manage the lifecycle of" your models, and Endpoints and Managed Training complete the path from notebook to served model.

Self-studyBigQuery ML or the platform, and a cap on the bill2 min▶

A workable rule: start in BigQuery ML when the training rows are already a query and a listed MODEL_TYPE fits; move to the platform when you need your own training code, a model from Model Garden, or a managed endpoint other systems call. The two meet: BigQuery ML can import TENSORFLOW, ONNX and XGBOOST models, so a model trained elsewhere can still be used with ML.PREDICT.

The platform also has a cost control BigQuery lacks. Google's spend-cap budgets cover a single project and a single eligible service, and the eligible list reads "Gemini API, Agent Platform (formerly known as Vertex AI), Cloud Run, and Cloud Run functions". BigQuery is not eligible, so BigQuery ML spend is guarded by the query controls from sessions 2 and 3, not by a cap. The launch stage of spend caps is reported as Preview, not confirmed on the page.

Real world

Two names for one bill. Tidewater's finance team sees "Agent Platform" on the invoice while the data team's runbook still says "Vertex AI" (constructed). Half a day goes on proving they are the same thing. The fix is one line in the runbook, both names side by side, and a spend-cap budget on the experiment project so a forgotten endpoint cannot run all month.

Build-along

A fare model, in SQL and on your laptop

★ 22 min · everyone builds

Two lanes, one model form: a linear regression of fare on trip miles and trip minutes. The first lane is the BigQuery ML SQL, to try in your own console; no output is pasted for it, because the build laptop had no billing-enabled project and these pages do not invent results. The second lane fits the same form on the session 1 sample with numpy and is pasted from a real run. It is not BigQuery ML; it is there so you can read what the SQL asks BigQuery to do.

What runs where. Runs in the BigQuery sandbox: no card, no billing account. That holds for the plain SELECT in step 1. Steps 2 and 3 are labelled "needs a billing-enabled project, confirm in your own console": whether the sandbox accepts CREATE MODEL is not documented as of 3 November 2026, so try them in your sandbox, and if they are refused, run them on a billing-enabled project. Replace YOUR_PROJECT with your project id and create a tw_lab dataset first, as in session 3.

Look at the training rows before you train on them. This is the AS SELECT of step 2 with the model removed: January 2019, positive and plausible miles and fares. Dry-run it first, as in session 2, and read the bytes estimate; then run it and look at the averages. No output is pasted; your numbers are your own.

★ Step 1 · sandbox SQL (expected, your numbers will differ)SELECT COUNT(*) AS trips, AVG(trip_miles) AS avg_miles, AVG(trip_seconds / 60) AS avg_minutes, AVG(fare) AS avg_fare FROM `bigquery-public-data.chicago_taxi_trips.taxi_trips` WHERE trip_start_timestamp >= TIMESTAMP '2019-01-01' AND trip_start_timestamp < TIMESTAMP '2019-02-01' AND trip_miles > 0 AND trip_miles < 50 AND fare > 0 AND fare < 200;

Train the model. LINEAR_REG is a built-in model type, so on demand this is the statement priced at the training rate from Part 1, on the bytes its query processes. input_label_cols names the label; trip_miles and trip_minutes become the features.

★ Step 2 · needs a billing-enabled project, confirm in your own consoleCREATE OR REPLACE MODEL `YOUR_PROJECT.tw_lab.fare_model` OPTIONS (model_type='LINEAR_REG', input_label_cols=['fare']) AS SELECT trip_miles, trip_seconds / 60 AS trip_minutes, fare FROM `bigquery-public-data.chicago_taxi_trips.taxi_trips` WHERE trip_start_timestamp >= TIMESTAMP '2019-01-01' AND trip_start_timestamp < TIMESTAMP '2019-02-01' AND trip_miles > 0 AND trip_miles < 50 AND fare > 0 AND fare < 200;

Evaluate it, then use it. Both are charged like ordinary queries. Compare the metrics the evaluation returns with the laptop numbers in step 7; expect them to differ, because the data, the month and the filters differ.

★ Step 3 · needs a billing-enabled project, confirm in your own consoleSELECT * FROM ML.EVALUATE(MODEL `YOUR_PROJECT.tw_lab.fare_model`); SELECT * FROM ML.PREDICT(MODEL `YOUR_PROJECT.tw_lab.fare_model`, (SELECT 5.0 AS trip_miles, 15.0 AS trip_minutes));

Now the laptop lane. Reuse the environment from builder session 1. It already has pyarrow 25.0.1 and numpy 2.4.6. The script also calls to_pandas(), so it needs pandas; the pandas version on the build laptop was not recorded, so it is left unpinned here.

★ Step 4 · setup (verified 3 November 2026, the session 1 environment). .venv/bin/activate pip install pyarrow==25.0.1 numpy==2.4.6 pandas

Load and clean the sample. Three columns, rows with gaps dropped, and range filters close to the SQL's, plus one the SQL does not have: trips between one minute and three hours.

★ Step 5 · b7_local_model.py, part 1# Builder session 7: the model BigQuery ML would train, fitted on a laptop with numpy least squares. # This is NOT BigQuery ML; it is the same idea (linear regression on fare) so you can read the SQL. # Needs: pip install pyarrow==25.0.1 numpy (numpy 2.4.6 here) import sys import numpy as np, pyarrow.parquet as pq SRC = sys.argv[1] if len(sys.argv) > 1 else "chicago_taxi_sample.parquet" t = pq.read_table(SRC, columns=["trip_miles", "trip_seconds", "fare"]).to_pandas().dropna() t = t[(t.trip_miles > 0) & (t.trip_miles < 50) & (t.trip_seconds > 60) & (t.trip_seconds < 3 * 3600) & (t.fare > 0) & (t.fare < 200)]

Hold out a fifth, fit, evaluate. A seeded random 20% is kept back for evaluation, the role ML.EVALUATE plays. lstsq fits an intercept and one weight per feature, which is what LINEAR_REG estimates too.

★ Step 6 · b7_local_model.py, part 2rng = np.random.default_rng(42) test = rng.random(len(t)) < 0.2 X = np.column_stack([np.ones(len(t)), t.trip_miles, t.trip_seconds / 60]) y = t.fare.to_numpy() w, *_ = np.linalg.lstsq(X[~test], y[~test], rcond=None) pred = X[test] @ w r2 = 1 - ((y[test] - pred) ** 2).sum() / ((y[test] - y[test].mean()) ** 2).sum() mae = np.abs(y[test] - pred).mean() print(f"training rows {int((~test).sum())}, evaluation rows {int(test.sum())}") print(f"fare = {w[0]:.2f} + {w[1]:.2f} x miles + {w[2]:.2f} x minutes") print(f"evaluation: r2 {r2:.3f}, mean absolute error ${mae:.2f}")

Run it and compare with this real output. Read the model as a fare card: about $2.76 to start, about $1.35 a mile, about $0.43 a minute, fitted on 11,896 of the 18,362 sampled trips (the ones that pass the sanity filters, minus the 20% held back), across 2013 to 2023, not on the city's whole history. An r2 of 0.883 means the two features explain most of the variation in fare on the held-out trips; the typical miss is $2.31.

★ Step 7 · python b7_local_model.py (real output, not BigQuery ML)training rows 11896, evaluation rows 2995 fare = 2.76 + 1.35 x miles + 0.43 x minutes evaluation: r2 0.883, mean absolute error $2.31

Check yourself

Three questions

Clear all three and builder session 7 gets stamped in your passport.

1 · On demand, what does BigQuery charge for training a built-in model such as LINEAR_REG?

Evaluation and prediction "incur the same charges as on-demand query jobs", $6.25 per TiB. Training is priced separately: "you must calculate CREATE MODEL job costs independently".

2 · Does Google document whether CREATE MODEL runs in the BigQuery sandbox?

The sandbox page's unsupported list is streaming, DML and the Data Transfer Service; BigQuery ML is not mentioned. An absent sentence is not a rule, so the answer comes from your console, not from these pages.

3 · Your notes say "deploy on Vertex AI Endpoints". What is the product called now?

The release notes rename nearly every component, Vertex AI Endpoints to Agent Platform Endpoints among them. Model Garden is the one that kept its name.
