Part 1 · covers buckets, location types and storage classes

A bucket is a location and a price ladder

5 min live

A Cloud Storage bucket holds objects, files with a name, and the bucket decides two things for every object in it: where it lives and, by default, which storage class it is billed as. Location types are a region ("a specific geographic place, such as Iowa"), a dual-region ("a specific pair of regions") or a multi-region ("a large geographic area that contains two or more geographic regions"). Classes trade a lower storage price for a minimum storage duration and a retrieval fee.

LivePick the class by how often the data is read3 min▶

Google's own guidance is in reading frequency. Nearline is "ideal for data you plan to read or modify on average once per month or less", Coldline "at most once a quarter", Archive for "data that you plan to access less than once a year". Standard has no minimum storage duration and no retrieval fee; Nearline has a 30-day minimum, Coldline 90 and Archive 365, and all three charge to read. For a data team that maps neatly onto zones: the landing zone and anything BigQuery reads every day stay Standard, last year's raw drops can go colder, and audit copies go to Archive.

If you cannot predict the reading pattern, Google offers Autoclass: "let Cloud Storage manage storage class transitions for you automatically". It is a sensible default for a bucket nobody owns the access pattern of yet.

Self-studyUniform bucket-level access, and why it is a one-way door2 min▶

With uniform bucket-level access, "Access Control Lists (ACLs) are disabled, and only bucket-level" IAM permissions grant access. Google says that "Generally, using uniform bucket-level access is recommended", and also that it "cannot be disabled after it has been active on a bucket for 90 consecutive days". It matters beyond tidiness: IAM Conditions on a bucket's allow policy need it switched on, and an organization can enforce it everywhere with the constraint storage.uniformBucketLevelAccess. Session 4 builds the IAM on top of it.

Part 2 · covers lifecycle rules and object naming

Names are the layout, rules are the schedule

5 min live

Cloud Storage has no folders, only object names with slashes in them, and every tool that reads a lake treats those names as the layout. BigQuery reads a hive-style layout directly: Google's own example is gs://my_bucket/my_table/dt=2019-10-31/lang=en/my_filename, where each key=value segment becomes a partition column. Lifecycle rules then act on those names and ages: "A lifecycle rule specifies exactly one of the following actions": Delete, SetStorageClass, or AbortIncompleteMultipartUpload.

LiveThree naming rules that save every later session3 min▶

Put the partition key in the name as key=value. BigQuery can then detect it: with source format AUTO "Key names and types are automatically detected", and with requirePartitionFilter a query without a filter on the key fails instead of reading everything. Prefix by zone and table first (sales/, loyalty/), so lifecycle rules can target one table with matchesPrefix, and IAM Conditions can target it with resource.name.startsWith. Write fewer, larger files than one per minute: every file is an object to list and open, and a reader pays that overhead per file.

Self-studyLifecycle conditions worth knowing2 min▶

Rules can combine conditions: age, createdBefore, matchesPrefix and matchesSuffix, matchesStorageClass, numNewerVersions and daysSinceNoncurrentTime for versioned buckets, sizeAboveBytes and others. Google caps the prefixes and suffixes at "up to 1000 prefixes and suffixes in total specified across all rules". A useful pair for a landing zone: SetStorageClass to Coldline at age 90 for sales/, and Delete at age 30 for tmp/. A rule applies to every object it matches, including objects already in the bucket, so read it twice before saving it on a production bucket.

Real world

The landing bucket that became the archive. A team points every source system at one bucket with default names. Two years later the bucket holds millions of small files, nobody can say which are still read, and no lifecycle rule can be written safely because the names carry no zone and no date. The fix is a rename, which on object storage means a full copy. The story is a constructed composite; the remedy, keys in names from day one, costs nothing at the start.

Part 3 · covers Parquet and why BigQuery prefers it

Columns on disk, columns on the bill

5 min live

CSV stores rows: to read one column you read every byte of every line. Parquet stores each column separately, compressed, with a footer that says where each column chunk sits, so a reader fetches only the columns it needs. BigQuery reads Parquet natively from Cloud Storage through external and BigLake tables, and BigQuery's own storage is columnar too: on-demand queries are charged by "the total data processed in the columns you select". The format of the landing zone decides how much every downstream read costs.

LiveTwo different savings, and which one BigQuery bills3 min▶

The file shrinks from 7,738,082 to 1,993,776 bytes, 25.8%, because Parquet stores types and compresses each column. That saves storage and network. The second saving is per query: a reader that needs one column fetches one chunk. Be precise about which one shows on a BigQuery bill. For tables stored in BigQuery, on-demand charges use BigQuery's documented logical sizes, 8 bytes per number, 2 plus the text length per string, not the compressed size on disk. So for native tables the lever is the columns and partitions you read, which session 3 measures; for external tables over Parquet, the file layout is what the engine has to open.

Self-studyExternal table or BigLake table over these files2 min▶

Both let BigQuery query files in Cloud Storage. An external table needs the reader to have access to the bucket as well. A BigLake table uses access delegation: "you grant users access only to the BigLake table, not to the underlying datastore", and it supports Avro, CSV, Delta Lake, Iceberg, JSON, ORC and Parquet. For a lake that more than one team reads, BigLake keeps one gate instead of two. Session 2 in the leader track, BigQuery is the warehouse and the lake, draws the difference.

Build-along

A partitioned lake on your laptop

★ 22 min · everyone builds

Four steps, one Python file, a few seconds of run time. The output at the end is pasted from a real run of exactly this code. Work in a fresh, empty folder; the later builder sessions reuse the sample file you download here.

Create an environment with the versions this page was verified on, and download the sample. The sample is 1,198,556 bytes: 18,362 trips from 132 seeded 15-minute slots, one per month from 2013 to 2023, with BigQuery's column names and types. Run in a new, empty folder.

★ Step 1 · setup (verified 3 November 2026, Python 3.11)python3 -m venv .venv && . .venv/bin/activate pip install pyarrow==25.0.1 duckdb==2.0.0 numpy==2.4.6 curl -O https://phoebefu6.github.io/learn-gcp-with-phoebe/data/chicago_taxi_sample.parquet

Write the same rows as CSV and as Parquet, and measure both. tw-lake is a local folder playing the landing bucket.

★ Step 2 · b1_layout.py, part 1import os, sys, glob, shutil import pyarrow.parquet as pq, pyarrow.csv as pacsv, pyarrow.compute as pc, pyarrow.dataset as ds SRC = sys.argv[1] if len(sys.argv) > 1 else "chicago_taxi_sample.parquet" LAKE = "tw-lake" # stands in for gs://tw-lake-prod-landing shutil.rmtree(LAKE, ignore_errors=True) t = pq.read_table(SRC) print("rows", t.num_rows, "columns", t.num_columns) os.makedirs(f"{LAKE}/flat", exist_ok=True) pacsv.write_csv(t, f"{LAKE}/flat/trips.csv") pq.write_table(t, f"{LAKE}/flat/trips.parquet", compression="snappy") for f in sorted(glob.glob(f"{LAKE}/flat/*")): print(f"{f:32s} {os.path.getsize(f):>12,d} bytes")

Write hive-style partitions by year, then ask for one year. write_to_dataset turns the year column into year=YYYY folders, the format BigQuery external tables detect. The dataset reader then prunes folders by the filter before opening any file.

★ Step 3 · b1_layout.py, part 2t = t.append_column("year", pc.year(t["trip_start_timestamp"])) pq.write_to_dataset(t, f"{LAKE}/sales_raw/taxi", partition_cols=["year"], basename_template="part-{i}.parquet") parts = sorted(glob.glob(f"{LAKE}/sales_raw/taxi/year=*/*.parquet")) print("partition files", len(parts), "first", parts[0], "last", parts[-1]) d = ds.dataset(f"{LAKE}/sales_raw/taxi", format="parquet", partitioning="hive") frags = list(d.get_fragments(filter=ds.field("year") == 2019)) print("files read for year = 2019:", len(frags), "of", len(parts)) print("rows in 2019:", d.to_table(filter=ds.field("year") == 2019).num_rows)

Run it and compare with this real output. Byte counts match exactly with pyarrow 25.0.1; another version may encode slightly differently. The 1,800 rows in 2019 are twelve 15-minute slots of 150 trips each, not a year of Chicago taxis.

Check yourself

Three questions

Clear all three and builder session 1 gets stamped in your passport.

1 · Last year's raw drops are read about once a quarter for audits. Which class fits, and what does it add?

Pick by reading frequency. Archive is for data read less than once a year; Coldline matches quarterly audits and adds a 90-day minimum and a charge to read.

2 · Why name objects sales/dt=2026-11-01/part-0.parquet instead of export_2026-11-01.csv?

Object storage has no folders, only names; the names are the layout every reader and rule works from. In the build-along the year= folders let a 2019 filter open 1 of 11 files.

3 · The Parquet file is 25.8% of the CSV. Does that cut a BigQuery on-demand bill for a native table by the same share?

The compression saving is real for storage and for files BigQuery reads externally. For native tables the bill follows logical bytes per column read, which session 3 and the bench measure.
