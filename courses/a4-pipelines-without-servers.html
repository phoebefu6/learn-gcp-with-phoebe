Pipelines without servers

Data does not arrive in BigQuery on its own. Files land, events fire, tables need rebuilding every night. Google Cloud offers at least four ways to do that work without anyone running a server, and each one bills on a different meter. Tonight we draw the four routes, follow an event through Pub/Sub, and finish with a short guide for choosing a route by the shape of the work rather than by whoever on the team knows the tool.

Part 1 · covers the four ways to move and transform data

Four routes into BigQuery

6 min live

Take one input: Tidewater's point-of-sale files landing in gs://tw-lake-prod-landing every night. There are four common ways to get them shaped and into BigQuery, and none of them asks you to patch a machine. They differ in what they are good at, in who on your team can maintain them, and above all in the meter each one runs on.

LiveThe four routes, in Google's words3 min▶

Scheduled SQL. A SQL statement BigQuery runs on a timetable. "Scheduled queries use features of BigQuery Data Transfer Service". It bills like any other query: bytes read on demand, or slot-hours on capacity. If the work is SQL and the data is already in BigQuery, nothing else needs to exist.

Dataflow. "Dataflow is a Google Cloud service that provides unified stream and batch data processing at scale", and "Dataflow executes Apache Beam pipelines." It bills worker vCPU and memory, shuffle data and, for streaming, Streaming Engine; usage "is billed in per second increments, on a per job basis".

Managed Service for Apache Spark (formerly Dataproc). Google's banner: the new name covers what was "Dataproc on Compute Engine" (clusters) and "Google Cloud Serverless for Apache Spark". The serverless form "lets you run Spark workloads without requiring you to provision and manage your own cluster". It suits teams that already have Spark code.

Cloud Run functions (formerly Cloud Functions). Small pieces of code that "can respond to asynchronous events, such as a message on a Pub/Sub topic, a change in a Cloud Storage bucket". One file lands, one function call validates it. It bills requests and compute time.

Self-studyWhy "serverless" does not mean "no bill to watch"2 min▶

None of the four routes has a machine for your team to patch, but each one has a meter that grows with use, and the meters do not look alike. Scheduled SQL grows with the bytes it reads, so a nightly rebuild that reads a whole history table every night costs more every month the history grows. Dataflow grows with worker time per job. Spark clusters, unless serverless, can run while nobody uses them. Functions grow with the number of calls, which follows the number of files or events.

So the owner of a route is also the owner of its meter. Prices for each are on the product's own pricing page; these pages quote only the BigQuery ones, in session 5, because they are the ones the builder bench verifies.

Real world

The Spark cluster that ran one SQL statement a day. A team migrating from an on-premises Hadoop estate moves its nightly jobs onto a managed Spark cluster, because that is what the jobs ran on before. A review a year later finds that most of the jobs read tables already in the warehouse and run one SQL statement each. Rewritten as scheduled SQL, they need no cluster at all, and the team retires a service nobody enjoyed maintaining. The story is a constructed composite of a common pattern.

Part 2 · covers events with Pub/Sub

Events arrive at least once

5 min live

Some data is not a file at all. When a shopper joins Tidewater's loyalty programme, the sign-up app publishes a message, and anything interested can receive it. Pub/Sub is Google Cloud's messaging service for that pattern: publishers send messages to a topic, and each subscription delivers them to one consumer. The detail a leader must carry out of the room is the guarantee it makes by default, because it decides how carefully the consumer has to be built.

LiveThree subscriptions, one default3 min▶

Google's subscription overview names three types. "Pull subscriptions use a subscriber client to request messages from the Pub/Sub server." "Push subscriptions use the Pub/Sub server to initiate requests to your subscriber application to deliver messages." "BigQuery subscriptions export data to a BigQuery table." Then the sentence that matters: "By default, Pub/Sub offers at-least-once delivery with no ordering guarantees on all subscription types."

"Pub/Sub also supports exactly-once delivery", with two limits from the exactly-once page: only the pull subscription type supports it, and "The exactly-once delivery guarantee only applies when subscribers connect to the service in the same region." Push and BigQuery subscriptions never get it. For Tidewater's loyalty sign-ups, landing straight in a table through a BigQuery subscription, that means the table can hold the same sign-up twice.

Self-studyWhy every event pipeline must be idempotent2 min▶

This conclusion is ours, derived from Google's guarantee: if delivery is at least once, a duplicate is a matter of when, not whether. A consumer is idempotent when processing the same message twice leaves the same result as processing it once. In practice that means each message carries a stable identifier (the sign-up's own id, not the time it arrived), and the consumer writes by that identifier, so a repeat overwrites rather than adds.

Ordering is the second half. With "no ordering guarantees", a "member updated" message can arrive before the "member joined" message it updates. Windows, late data and ordering design are a subject of their own, taught in Learn Streaming Data with Phoebe. The leader's job is to ask, in every design review that involves events: what happens when this message arrives twice, or out of order?

Real world

The welcome bonus paid twice. A loyalty programme credits a welcome bonus on every sign-up message it receives. During a brief outage the messaging service redelivers a batch of messages, exactly as its at-least-once contract allows, and several hundred members get their bonus twice. Nothing malfunctioned. The consumer was written as if each message would arrive once. The story is a constructed composite; the delivery guarantee is Google's.

Part 3 · covers choosing by workload

Choose by the shape of the work

4 min live

Teams often pick a pipeline tool by who is in the room: the Spark person proposes Spark, the Python person proposes a function. A better habit is to ask four questions in a fixed order and take the first yes. The guide below is constructed by us from the products' documented purposes; it is a starting point for a design review, not a Google rule.

LiveThe limits that decide between a function and a job2 min▶

Cloud Run runs code in several shapes: "your code can run as a service, job, worker pool, or instance." Two of them matter for pipelines, and their time limits decide which one fits. A request to a service or function times out "by default to 5 minutes (300 seconds) and can be extended up to 60 minutes (3600 seconds)". A job's tasks run "for a maximum of 10 minutes" by default and can be set up to 168 hours (7 days).

The practical reading: a function per file is right when each file can be handled in seconds to minutes. A monthly file that takes two hours to process does not belong in a request; it belongs in a job, or in Dataflow. Builder session 6 writes and runs a function on a laptop and shows where the limits bite.

Self-studyWhen the routes need an orchestrator2 min▶

Real flows chain routes: a function validates a file, then a SQL statement rebuilds a curated table, then a feature table refreshes. Something has to run them in order and retry the failures. Google Cloud's managed Airflow service is Cloud Composer, which "is evolving to become Managed Service for Apache Airflow"; these pages name it and stop there. How to design orchestration, dependencies, retries and backfills, lives in Learn Data Orchestration with Phoebe.

One honest gap. Several secondary sources say a scheduled query cannot run more often than every five minutes. We could not read that rule verbatim on Google's scheduling page, so treat it as reported, and confirm it in the console before you design around it.

Real world

The function that ran out of time once a month. A file-validation function works perfectly every night, until month end, when the finance export is many times larger and the call hits its request timeout. The fix is not a bigger function. The month-end file moves to a job with a longer task limit, and the nightly files stay where they were. The story is constructed; the timeouts are Google's.

Build-along

Route Tidewater's five flows

★ 22 min · everyone builds

Paper only. Tidewater, constructed for these pages, has five data flows: point-of-sale sales files every night, loyalty sign-ups as events, supplier price CSVs every week, a churn feature table, and a daily KPI table for the store managers. For each one, write how it arrives, which route it takes, which meter it runs on, and who owns that meter. Use the four questions from Part 3 in order.

Write how each flow arrives. Files on a schedule, events one at a time, or data already sitting in BigQuery tables. This one column answers most of the routing.

Work the first row together. The point-of-sale files land nightly, one per store. Each needs a light check before it is trusted.

★ Worked example: POS sales filesFlow: POS sales files, one per store per night Arrives: files in gs://tw-lake-prod-landing/sales/dt=.../ Q1: not yet in BigQuery -> no Q2: light check per file on arrival -> yes Route: Cloud Run function per file, writes to sales_raw Meter: requests and compute seconds Owner: data-eng (raj) Then: scheduled SQL builds sales_curated from sales_raw (second route, second meter: bytes read)

Route the other four with the four questions. Ask them in order and stop at the first yes. Write the meter beside each route, and mark any flow that arrives as events with "must be idempotent".

★ One defensible answer: the daily KPI tableFlow: daily KPI table for store managers Arrives: computed from sales_curated, already in BigQuery Q1: data in BigQuery, SQL is enough -> yes Route: scheduled SQL Meter: bytes read (name the columns; session 5 prices it) Owner: analytics lead

Name an owner for every meter. One person per row who answers when that route's cost jumps or its data is late. If one person owns all five, write it down: that is a staffing finding.

Repeat for three of your own flows. Circle any route chosen because "that is what we already know" rather than by the four questions. Those are the ones to revisit first.

✗ The routing sheet that grows a service per flowa Spark cluster for the nightly SQL, because the jobs ran on Spark before a streaming pipeline for a weekly CSV an event consumer that adds a row for every message it receives

Ask "is it already in BigQuery?" first. If the answer is yes and the transformation is SQL, every other route adds a service, a meter and an owner for no gain. The first question in the guide is first on purpose.

Homework

Before session 5

30 min
  1. List your pipelines. Ask your data team for every scheduled or event-driven flow that writes to BigQuery, and which service runs it.
  2. Find one that could be SQL. Look for a job on Spark or Dataflow whose input is already in BigQuery and whose work is a single query.
  3. Ask the duplicate question. For one event-fed flow, ask what happens when the same message arrives twice. Write down the answer, including "we do not know".
  4. Find the biggest scheduled query. Note how often it runs and how many columns it reads. Session 5 turns exactly that into a monthly bill.
Check yourself

Three questions

Clear all three and leader session 4 gets stamped in your passport.

1 · What does Pub/Sub guarantee by default, on all subscription types?

"By default, Pub/Sub offers at-least-once delivery with no ordering guarantees on all subscription types." Exactly-once exists, but only on pull subscriptions in the same region, so consumers should expect duplicates.

2 · Tidewater's daily KPI table is computed from sales_curated, which is already in BigQuery, and the logic is one SQL statement. Which route fits best?

The first question in the guide is "data already in BigQuery, and SQL is enough?". Scheduled queries "use features of BigQuery Data Transfer Service" and bill bytes read or slot-hours like any query.

3 · What does Dataflow execute?

"Dataflow executes Apache Beam pipelines", and it "provides unified stream and batch data processing at scale". Builder session 5 runs a Beam pipeline on a laptop.
