Part 0

Where we start

Every request to Google Cloud is a question: may this principal use this permission on this resource? Google answers it in a documented order. "IAM always checks relevant deny policies before checking relevant allow policies." Then "The effective allow policy for a resource is the union of the allow policy set at that resource and the allow policy inherited from its parent." Anything that is neither denied nor allowed is not granted. Tonight's company is Tidewater Grocers, a constructed APAC grocery chain: organization tidewater.example, folders data-platform, analytics and sandbox, and the production project tw-lake-prod with datasets sales_raw, sales_curated and loyalty_pii.

Part 1 · covers a dataset-level grant

Grant the dataset, not the project

5 min live

Analysts at Tidewater need to read curated sales and nothing else. The precise grant is the predefined role BigQuery Data Viewer, roles/bigquery.dataViewer, on the dataset sales_curated, given to the group analysts@tidewater.example. Predefined roles are "managed by Google Cloud services", and this one holds 27 permissions in the roles reference read on 3 November 2026: BigQuery reads such as bigquery.tables.getData, a few Knowledge Catalog (formerly Dataplex) scan reads, and two project reads. Not one of them starts with storage..

LiveWrite the binding, then read the policy back3 min▶

A binding is one role given to one or more members on one resource. On a dataset it can be added from the console's Share menu or with the bq tool. Reading a policy back is the other half of the job: gcloud projects get-iam-policy prints the project's allow policy as a list of bindings, each a role, its members and an optional condition. The shape below is constructed for Tidewater, and Google's exact output can carry more fields, so treat it as a reading guide rather than a template.

★ Shown, needs a real project · grant on one dataset (check the syntax in bq help on your version)bq add-iam-policy-binding \ --member="group:analysts@tidewater.example" \ --role="roles/bigquery.dataViewer" \ tw-lake-prod:sales_curated
★ Shown, constructed output shape · gcloud projects get-iam-policy tw-lake-prod --format=json{ "bindings": [ { "role": "roles/bigquery.dataEditor", "members": ["serviceAccount:ingest-pipeline@tw-lake-prod.iam.gserviceaccount.com"], "condition": { "title": "sales_raw only", "expression": "resource.name.startsWith('projects/tw-lake-prod/datasets/sales_raw')" } }, { "role": "roles/bigquery.jobUser", "members": ["serviceAccount:ingest-pipeline@tw-lake-prod.iam.gserviceaccount.com"] } ] }

Notice what the project policy does not show: the analysts' dataset grant lives on the dataset, and the data-engineering grant lives on the folder. To answer "who can read this table?" you read every level from the table up to the organization and take the union. That is exactly what the evaluator in the build-along does.

Self-studyWhy not a basic role2 min▶

Basic roles "include thousands of permissions across all Google Cloud services. In production environments, do not grant basic roles unless there is no alternative." The bench in session 8 shows the size of the mistake on a modelled role list: one roles/editor grant on tw-lake-prod takes mei from 27 permissions on sales_curated.orders to 320 of the 334 modelled. There is a second cost too: "you can't add conditions to role bindings for legacy basic roles", so a basic role can never be narrowed the way Part 2 narrows the pipeline.

Real world

The analyst who could read the landing bucket. A team grants its analysts Viewer on the whole project "so they can see BigQuery". Viewer is a basic role across every service, so the same grant opens the raw files in Cloud Storage, including columns the curated tables had dropped. The fix is the grant above: one predefined BigQuery role on one dataset. The story is a constructed composite.

Part 2 · covers a service account for the pipeline, with a condition

A pipeline identity with a fence of its own

5 min live

The ingest pipeline is not a person, so it runs as a service account, "a special kind of account typically used by an application or compute workload", "identified by its email address": ingest-pipeline@tw-lake-prod.iam.gserviceaccount.com. It needs to write sales_raw and nothing else. Tidewater gives it BigQuery Data Editor on the project, narrowed by an IAM Condition written in CEL, plus BigQuery Job User so it can run load jobs. A conditional binding grants only while its expression is true.

LiveWhy a condition beats a second project3 min▶

The alternative is to move sales_raw into its own project so a plain project grant is narrow enough. That doubles the billing links, the deny policies and the places to look. A condition keeps one project and narrows one binding: resource.name.startsWith('projects/tw-lake-prod/datasets/sales_raw') is Google's documented attribute pattern, the same one the conditions page shows for buckets. Two limits from that page: "Only some resource types accept conditions in role bindings", so confirm yours does, and you cannot add conditions to legacy basic roles.

The trap is in the string. startsWith is a plain prefix test, so the expression above would also match a future dataset called sales_raw_archive. That reading is ours, derived from how a prefix test works, not a sentence on Google's page. Ending the prefix with a slash, .../datasets/sales_raw/, closes the gap for the tables inside, but then the dataset resource itself no longer matches, so decide which you need and test both.

Self-studyKeys are the risk, not the account2 min▶

Google's service account page is direct: "Service account keys are a security risk if not managed correctly", and "You should choose a more secure alternative to service account keys whenever possible." In practice that means letting the workload run as its service account through the platform it runs on, rather than downloading a key file. An organization can enforce that with the Organization Policy constraint iam.disableServiceAccountKeyCreation. Organization Policy "focuses on what" can be configured; IAM "focuses on who".

Real world

The ingestion account that could rewrite the reports. A pipeline is given Data Editor on the whole project to get it working before a deadline, and the narrowing is left for later. Months on, a bug in a backfill job overwrites a curated table the finance dashboard reads. A one-line condition would have turned the write into "not granted". The story is a constructed composite.

Part 3 · covers a deny policy

A deny rule that grants are not allowed to lower

5 min live

Allow policies only add. Because the effective policy is a union, a grant higher up cannot be taken back by a narrower policy lower down; that conclusion is derived from Google's "union" wording, not a sentence of Google's. Deny policies are the tool that subtracts. Each one "is attached to an organization, folder, or project" and inherited downward, and IAM checks it first. Its rule has denied principals, exception principals, denied permissions, exception permissions and a denial condition, and denial conditions "only recognize resource tag functions".

LiveThe rule, written out3 min▶

Below is Tidewater's rule in the same shape the evaluator reads, constructed to match its fixture. Denied permissions use Google's format SERVICE_FQDN/RESOURCE.ACTION; the deny page's own example is iam.googleapis.com/roles.delete, so check that each permission you deny appears on the page of permissions supported in deny policies before relying on it. Google caps a resource at 500 deny policies holding 500 deny rules in total. Before applying a real policy, check the principal identifier format the deny policies page asks for.

★ Constructed, matches the evaluator's fixture · deny.json{ "displayName": "only-the-pipeline-writes-prod", "rules": [{ "denyRule": { "deniedPrincipals": ["principalSet://goog/public:all"], "exceptionPrincipals": [ "serviceAccount:ingest-pipeline@tw-lake-prod.iam.gserviceaccount.com" ], "deniedPermissions": ["bigquery.googleapis.com/tables.updateData"], "denialCondition": { "title": "prod only", "expression": "resource.matchTag('1001/env', 'prod')" } } }] }
★ Shown, needs a real project · attach it (check flags on your gcloud version)gcloud iam policies create only-the-pipeline-writes-prod \ --attachment-point=cloudresourcemanager.googleapis.com/projects/tw-lake-prod \ --kind=denypolicies \ --policy-file=deny.json
Self-studyExceptions skip a deny; they grant nothing2 min▶

Exception principals are "exempt from the deny rule". That is all. The pipeline passes the deny because it is the exception, then still needs an allow binding to write, which is why c09, a write to sales_curated, comes back "not granted" with the deny skipped. The bench's case c27 tests the same trap. For column-level fences inside a table, BigQuery uses policy tags; the concepts behind row and column security are taught in data access control.

Real world

The data engineer who fixed production by hand. During an incident an engineer with folder-wide Data Editor patches rows in a production table directly, the patch is wrong, and the pipeline's next run cannot reconcile it. A deny on production writes, with the pipeline as the only exception, turns that well-meant patch into a refused request and a conversation. The story is a constructed composite.

Build-along

Five requests, traced

★ 22 min · everyone builds

You run an evaluator that applies Google's documented order to Tidewater's constructed policies: the three you wrote tonight, plus a few more on the organization and folders. It prints each verdict, the step that decided it, the level where that happened, and a trace of the rules it read on the way. Predict each verdict before you run it.

On a billing-enabled project (optional). Shown, needs a billing-enabled project: the BigQuery sandbox covers BigQuery only, and the $300 Free Trial asks for a card. Everything below runs on your laptop instead; the bq and gcloud boxes above are shown so you recognise them at work.

Set up. No extra packages: the evaluator is Python 3.11 standard library only. Use session 1's environment or any Python 3. Put b4_iam.py next to the evaluator files, iam_eval.py, its fixture iam-fixture.json and the roles file roles-2026-11-03.json, or pass their folder as the first argument. iam_eval.py is the Python twin of the evaluator behind builder session 8's bench.

★ Step 1 · b4_iam.py, part 1# Builder session 4: ask the evaluator what Google's IAM rules say about five Tidewater requests. # Same logic as the bench (iam_eval.py, the Python twin of the bench's gcp-iam.js). import sys sys.path.insert(0, sys.argv[1] if len(sys.argv) > 1 else ".") import iam_eval as I

Ask five questions. Each case is a principal, a permission and a resource. The evaluator returns the verdict, the step that decided it (deny, allow or none), the level, and a trace of every rule it read and set aside.

★ Step 2 · b4_iam.py, part 2for cid in ["c05", "c06", "c08", "c09", "c12"]: c = next(x for x in I.FIX["cases"] if x["id"] == cid) q = c["request"] r = I.evaluate(q) where = r.get("at", "-") print(f"{cid} {q['principal'].split(':')[1]:52s} {q['permission']:28s} on {q['resource']:13s} -> {r['verdict']:11s} ({r['step']} at {where})") for line in r["trace"]: print(" trace:", line)

Run it and compare with this real output. Read c05's trace: the organization's PII fence was checked and set aside because its condition was false for a table without the pii tag. Read c09's: the deny was skipped because the account is the exception, and then the conditional binding failed, so nothing granted it.

Check yourself

Three questions

Clear all three and builder session 4 gets stamped in your passport.

1 · raj has Data Editor on the folder data-platform. Why is his write to sales_raw.orders denied (c06)?

"IAM always checks relevant deny policies before checking relevant allow policies." The folder grant is real (c05 shows raj can read), but it never gets a say on the write.

2 · The pipeline is the deny rule's exception. Why can it still not write sales_curated.orders (c09)?

Skipping the deny is only step 1. Step 2 still needs a binding whose condition is true, and the only one is fenced to sales_raw.

3 · What does an exception principal in a deny rule do?

Google's wording is "exempt from the deny rule". Exempt is not allowed; c09 and the bench's c27 both show it.

OrderDeny policies first, then the union of allow policies, then not granted.
Grant smallA predefined role on the dataset: roles/bigquery.dataViewer on sales_curated.
ConditionsCEL on one binding: resource.name.startsWith(...). Mind the prefix.
DenyOn org, folder or project; inherited down. Conditions read tags only.
ExceptionsExempt from the deny; still need an allow to do anything.
Service accountsOne per workload, no keys where avoidable; enforce with an Org Policy constraint.
