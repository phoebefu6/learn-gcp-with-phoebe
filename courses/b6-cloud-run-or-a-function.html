Cloud Run or a function

Between a file landing in a bucket and a row in BigQuery there is usually a small piece of code: check the name, pick the table, start the load. On Google Cloud that code runs on Cloud Run, as a service, a job or a function. Tonight you learn which shape fits which work, how the landing event reaches your code, and you run Tidewater's ingest handler on your laptop, feeding it one good path and one bad one.

Part 1 · covers services, jobs and functions on Cloud Run

One platform, three shapes of work

5 min live

Google's What is Cloud Run page puts it in one line: "On Cloud Run, your code can run as a service, job, worker pool, or instance." Functions live there too. On 22 August 2024 Google announced that "Cloud Functions and its familiar event-driven programming model is now Cloud Run functions", adding "This goes beyond a simple name change. We've unified the Cloud Functions infrastructure with Cloud Run". So Cloud Run functions (formerly Cloud Functions) is not a separate product any more; it is the smallest shape on the same platform.

LiveService, job, function: what each is for3 min▶

Service. "Cloud Run services are great for code that handles requests, events, or functions." A service waits for traffic. Each request has a deadline: "The timeout is set by default to 5 minutes (300 seconds) and can be extended up to 60 minutes (3600 seconds)."

Job. "A job can start a single instance to run your code", and the instance stops when the work is done. "By default, each task runs for a maximum of 10 minutes", and a task can be allowed "up to 168 hours (7 days)". A nightly backfill that runs for two hours is a job, not a service.

Function. "Cloud Run functions can respond to asynchronous events, such as a message on a Pub/Sub topic, a change in a Cloud Storage bucket, or a Firebase event." You write one handler; the platform does the rest.

Self-studyWhat the rename did not break2 min▶

The rename post is explicit about continuity: "we are committed to continuing support for the existing functions APIs, gcloud commands and Terraform modules." That is why the deploy box at the end of the build-along still shows gcloud functions deploy next to gcloud run deploy. When you read older guides, blog posts or exam material that say "Cloud Functions", read it as Cloud Run functions; the event-driven model is the same, the infrastructure underneath is Cloud Run's.

If your team manages Cloud Run in code, that belongs to learn-terraform, session 4; these pages use the console and gcloud.

Real world

The export that kept dying at the hour. A team runs a nightly export as a Cloud Run service behind a scheduler call. It works for months, then the data grows and the request starts failing at the deadline. Raising the timeout buys a few weeks; the ceiling is 60 minutes. Moving the export to a job, whose tasks can run for hours, ends it. The story is a constructed composite; the numbers are Google's documented limits.

Part 2 · covers container or function for ingest

How much of the container do you want to own?

5 min live

Every shape on Cloud Run ends up as a container. The question is who writes it. With a function you hand over a few files of source code and a stock language runtime; with a service or job you write the Dockerfile and own everything in the image. For an ingest step that checks a file name and starts a load, a function is usually enough. The moment you need a system library, several endpoints, or hours of work, the container earns its keep.

LiveThree signals that you have outgrown a function3 min▶

You need something the stock runtime does not have, a system library or a binary tool: write the image yourself. You need several routes in one app, an API rather than a single handler: that is a service. The work outlasts a request: anything that can run past the service ceiling of 60 minutes belongs in a job, whose tasks can run up to 168 hours.

None of the three applies to tonight's handler. It reads two fields, checks one regular expression and returns a decision, so it stays a function.

Real world

The function that needed one more library. Tidewater's supplier invoices arrive as PDFs (constructed). The first version is a function that only moves files. Then finance wants the totals read out of each PDF, which needs a system tool the stock runtime does not ship. Raj moves the same handler into a container he writes, deployed as a service. Part 3 · covers triggers and the free tier

From a landed file to a loaded partition

5 min live

A function does nothing until something calls it. For ingest, the caller is an event: an object lands in the landing bucket, a message reaches Pub/Sub, a trigger invokes the code. Google's trigger page offers two routes, and its advice is direct: "Direct Pub/Sub trigger (Recommended)", or Eventarc, "Use this if you need Eventarc's advanced filtering or routing features." Whichever you pick, one property of Pub/Sub shapes how you write the handler.

LiveAt-least-once means write it to run twice3 min▶

Pub/Sub's own overview: "By default, Pub/Sub offers at-least-once delivery with no ordering guarantees on all subscription types." Exactly-once delivery exists, but only on pull subscriptions and only "when subscribers connect to the service in the same region"; push and export subscriptions do not support it. So plan for the same landing event reaching your handler twice, and in any order.

The professional answer is an idempotent handler: running it twice leaves the same result as running it once. For ingest that usually means the target is decided by the file, not by the clock, and the load replaces that day's partition rather than appending to it. Tonight's handler does the first half: the target partition comes from the dt= in the name, so a duplicate event names the same partition. Pub/Sub design in depth lives in learn-streaming-data.

Self-studyThe free tier, and the spend cap that now covers Cloud Run2 min▶

Cloud Run's pricing page lists a free tier for request-based billing, "based on us-central1 active pricing": the first 180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests free per month. Cloud Run functions get "2 million invocations per month (includes both background and HTTP invocations)". The free usage "is aggregated across projects by billing account and resets every month", so ten small projects share one allowance. Read on 3 November 2026; free tiers change, so re-verify on the Cloud Run pricing page.

Budgets on their own only alert: "Setting an alerts-only budget doesn't automatically cap ... spending." Google's newer spend-cap budgets do stop spend, for a single project and a single eligible service, and the eligible list includes "Cloud Run, and Cloud Run functions". BigQuery is not on that list. The launch stage of spend caps is reported as Preview, not confirmed on the page we read.

Real world

The day the sales doubled. A retailer's dashboard shows one store's takings twice over for a single day. The cause is a redelivered landing event and a load that appended the same file a second time. Nothing failed, so nothing alerted. The fix is in the handler, not the dashboard: name the partition from the file and replace it on every load. The story is a constructed composite of a common failure.

Build-along

An ingest function on your laptop

★ 22 min · everyone builds

Four steps, one Python file, two terminal windows. The functions framework serves your handler on localhost:8080, exactly as it would serve it inside Cloud Run, and curl plays the part of the landing event. The output at the end is pasted from a real run of exactly this code, with functions-framework 3.10.2 on Flask 3.1.3.

Reuse the environment from builder session 1 and add the functions framework. Activate the same .venv as in session 1. The framework pulls in Flask; on the build laptop that was Flask 3.1.3.

★ Step 1 · setup (verified 3 November 2026, the session 1 environment). .venv/bin/activate pip install functions-framework==3.10.2

Write the handler. Save this as main.py. The regular expression is session 1's naming rule written as code: sales/, then dt= and a date, then one Parquet file. Anything else is refused with HTTP 400, so a bad file is loud on day one instead of silent in a dashboard.

★ Step 2 · main.py# Builder session 6: an ingest function, run locally with functions-framework (no Cloud Run needed). # Needs: pip install functions-framework==3.10.2 # Run: functions-framework --target=ingest --port=8080 import re import functions_framework HIVE = re.compile(r"^sales/dt=(\d{4}-\d{2}-\d{2})/[^/]+\.parquet$") @functions_framework.http def ingest(request): event = request.get_json(silent=True) or {} bucket, name = event.get("bucket", ""), event.get("name", "") m = HIVE.match(name) if not m: return {"status": "rejected", "reason": "path is not sales/dt=YYYY-MM-DD/*.parquet", "name": name}, 400 return {"status": "accepted", "load": f"gs://{bucket}/{name}", "into": f"tw-lake-prod.sales_raw.orders${m.group(1).replace('-', '')}"}, 200

Serve it. In the folder that holds main.py, start the framework and leave this terminal running. --target names the function to serve; 8080 is the framework's default port, written out here so it is visible.

★ Step 3 · terminal 1functions-framework --target=ingest --port=8080

Send one good path and one bad one, and compare with this real output. Run the two curl lines in a second terminal. The accepted reply names the load target as tw-lake-prod.sales_raw.orders$20261101: the handler appends the file's date, without dashes, after a $, which is the form it uses to name one day's partition of the orders table as the target. The handler only decides; it does not start a real load, which would need a billing-enabled project. The final line is the HTTP status of the second request.

★ Step 4 · terminal 2 (real output)$ curl -s -X POST localhost:8080 -H "Content-Type: application/json" -d '{"bucket":"tw-lake-prod-landing","name":"sales/dt=2026-11-01/part-0.parquet"}' {"into":"tw-lake-prod.sales_raw.orders$20261101","load":"gs://tw-lake-prod-landing/sales/dt=2026-11-01/part-0.parquet","status":"accepted"} $ curl -s -X POST localhost:8080 -H "Content-Type: application/json" -d '{"bucket":"tw-lake-prod-landing","name":"sales/2026-11-01.csv"}' {"name":"sales/2026-11-01.csv","reason":"path is not sales/dt=YYYY-MM-DD/*.parquet","status":"rejected"} HTTP 400

Homework

Before session 7

30 min
  1. Add a third case. Send sales/dt=2026-11-31/part-0.parquet. The regex accepts it, but the date does not exist. Change the handler so it rejects impossible dates too, and decide which HTTP status you would return.
  2. Route by prefix. Extend the handler so loyalty/dt=.../*.parquet goes to a loyalty_pii target and everything else is refused. Who at Tidewater should be told when a loyalty file is rejected?
  3. Prove it is idempotent. Send the accepted request twice. Write down why two identical answers are what you want, and what the real load would have to do for the second one to be harmless.
  4. Classify three jobs. Take three pieces of code your team runs on a schedule or on an event. Label each function, service or job, using Part 2's three signals.
Check yourself

Three questions

Clear all three and builder session 6 gets stamped in your passport.

1 · How long can a single request to a Cloud Run service run, at most?

Five minutes is the default, 60 the ceiling. Ten minutes and 168 hours are the default and maximum for a job's task, which is why long work goes to a job.

2 · A 2023 guide tells you to "deploy a Cloud Function". What is that product called now?

The event-driven model kept working, and Google committed to supporting the existing functions APIs and gcloud commands. Only the name and the infrastructure underneath changed.

3 · Why must an ingest handler fed by Pub/Sub tolerate receiving the same file event twice?

Exactly-once delivery exists only for pull subscriptions in the same region. Design for duplicates: derive the target from the file and replace rather than append.
