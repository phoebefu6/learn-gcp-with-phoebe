Part 0

Where we start

You know two things from session 2: a query's price is the columns it names times the rows it scans, and the estimate is visible before you run. Naming fewer columns was the first lever. Tonight adds the second and third: scanning fewer rows, by partition, and fewer storage blocks, by cluster. One rule for the whole evening: a saving you can count before running is exact; a saving only the run can count is modelled until you measure it. Part 1 · covers the three partitioning types

Three ways to slice a table

5 min live

A partitioned table is stored as slices, and a query that filters on the partitioning column only reads the slices it needs. BigQuery offers three ways to cut. By a time-unit column, a date or timestamp column in your own data. By ingestion time, where BigQuery stamps each row with the time it was loaded in the pseudo-column _PARTITIONTIME, hourly, daily, monthly or yearly. Or by an integer range, with a start, an end and an interval; Google's own example cuts customer_id from 0 to 100 in steps of 10.

Liverequire_partition_filter: make the cheap query the only query3 min▶

Partitioning only saves money when the query filters on the partitioning column. People forget. The table option require_partition_filter = TRUE turns that forgetting into an error: a query on the table without a filter on the partitioning column is refused instead of reading every partition. Session 1 met the same switch for hive-partitioned files, requirePartitionFilter. Set it on any large partitioned table that people query by hand; the first refused query teaches the habit faster than any guideline.

Self-studyChoosing the type2 min▶

Use a time-unit column when the data carries the time people filter on, as the taxi trips do with trip_start_timestamp: an event's own time is what analysts ask about. Use ingestion time when rows arrive without a trustworthy timestamp, or when "what did we load yesterday" is the real question. Use an integer range when the filter is a numeric key, a store number or a customer bucket, with evenly spread values. A rule of thumb that is ours, not Google's: if nobody filters on the column, it is the wrong partitioning column, however natural it looks.

Real world

The events table partitioned on the wrong day. A team partitions its sales events by load time because the pipeline is easy that way, then every analyst filters on the sale date. Late-arriving files spread one sale day across many load days, so every query reads far more slices than it needs. Re-partitioning on the sale date fixes it, at the cost of rewriting the table once. The story is a constructed composite.

Part 2 · covers clustering and column order

Sorted blocks inside each slice

5 min live

Clustering works inside the slices. In Google's words, "Clustered tables in BigQuery sort data in storage blocks based on the values in user-defined clustered columns". A filter on a clustered column can then skip every block whose values cannot match. The catch is the timing: "the number of blocks to scan isn't known until a query runs", so you do not get an accurate estimate before execution. Partitioning is planned; clustering is discovered.

LiveColumn order matters3 min▶

A table can be clustered by several columns, and the order you list them in is the order the rows are sorted. Google's clustered-tables page explains that order matters: the sort is by the first column, then by the second within equal values of the first, and so on. So a filter on the first clustered column can skip blocks well; a filter only on the second or third, with nothing on the first, usually cannot, because those values are scattered across the blocks. Put first the column people filter on most, and filter on it in your queries.

For the taxi table, pickup_community_area first makes sense if dashboards are cut by area. If they are mostly cut by company, it should be company. The data does not decide this; the queries do.

Self-studyHow the bench models what Google does not publish2 min▶

Google does not publish block sizes or how a real clustered table is laid out, so the bench uses a stated model: each January 2019 day partition sorted by pickup_community_area, NULLs first, cut into blocks of 5,000 rows, and a filter reads every block its value touches. Under that model, area 56 (Midway) touches 36 of 257 blocks in January, 172,753 rows. That is a teaching model, labelled modelled wherever it appears. The real figure comes from running the query and reading the bytes billed in the job details.

Real world

Clustered by the column nobody filters on first. A loyalty table is clustered by (member_tier, store_id) because tier was the first column in the source file. Every report filters by store. The clustering helps almost nothing until the order is swapped. The story is a constructed composite.

Part 3 · covers measuring the saving honestly

The ladder, rung by rung

5 min live

Here is one question asked of the full taxi table four ways, computed from BigQuery's documented logical sizes per data type and the table's 211,670,894 rows. Each rung adds one lever. The first three rungs are exact arithmetic on documented rules and exact row counts. The fourth is modelled. Saying which is which is part of the job.

LiveExact savings and modelled savings3 min▶

Columns are exact. Logical sizes are documented per type, 8 bytes for an INT64, FLOAT64 or TIMESTAMP, 2 bytes plus the text length for a STRING, so three columns instead of 23 is arithmetic: 77.03 GiB becomes 4.58 GiB. Partitions are exact. January 2019 has 1,213,529 trips, an exact count from the city's portal, so a filter on that month reads exactly those rows: 0.0263 GiB, billed at 27 MB because charges round up to the nearest MB. Clustering is modelled. The 36 of 257 blocks come from the bench's block model, and Google says the number of blocks to scan is not known until a query runs. The dry run on a clustered table is therefore an upper bound, and the real saving can be larger or smaller than the model's.

One more honest note: the last rung processes 0.0037 GiB but bills 10 MB, because BigQuery charges "a minimum 10 MB data processed per table referenced by the query". Past a point, cutting bytes no longer shows on the bill.

Self-studyMeasure it yourself on the real table2 min▶

After the build-along, run the same three-column query on your new table twice, once filtered to one day and once filtered to one day and area 56. Open each job's details and note the bytes processed and billed. The partition rung should match the exact arithmetic closely for your one day; the cluster rung is the number that replaces the model for your table. Record both, with the date, because Google can change storage internals without notice.

Real world

The clustering win that was already a partition win. A team reports a large saving from adding clustering, but they added a date filter on the partitioned column in the same change. Measured rung by rung, nearly all of the saving was the partition filter. The story is a constructed composite; the lesson is to add one lever at a time and measure each.

Build-along

A January table and the bytes ladder

★ 22 min · everyone builds

Two halves. In the sandbox you create a partitioned, clustered copy of January 2019 and watch the partition filter work, and refuse. On your laptop you compute the four rungs from the bench's engine, so the numbers you saw in Part 3 come out of code you can read.

In the sandbox. Runs in the BigQuery sandbox: no card, no billing account. Steps 1 and 2 run there and their outputs are "expected, your numbers will differ". CREATE TABLE ... AS SELECT is DDL, a statement that defines a table; the sandbox's unsupported list names DML, the statements that change rows, such as INSERT and UPDATE. If your sandbox still refuses the statement, its error message says why; read it before changing anything.

Create a dataset and the January table. In the Explorer, create a dataset named tw_lab in your sandbox project, in the same location the public chicago_taxi_trips dataset shows on its Details tab. Then dry-run the statement below before you run it. Whether the public source table is itself partitioned is not verified on these pages, so budget for the worst case, a full 23-column read about the size of the bench's SELECT * rung, 77.03 GiB of your free 1 TiB, and let the dry run show the real number. The new table stores about January's 1,213,529 trips; at the bench's 390.7 logical bytes per row that is modelled at about 0.44 GiB, well inside the 10 GiB lifetime storage.

★ Step 1 · sandbox DDL (expected, your numbers will differ)CREATE TABLE `YOUR_PROJECT.tw_lab.trips_jan2019` PARTITION BY DATE(trip_start_timestamp) CLUSTER BY pickup_community_area OPTIONS (require_partition_filter = TRUE, partition_expiration_days = 60) AS SELECT * FROM `bigquery-public-data.chicago_taxi_trips.taxi_trips` WHERE trip_start_timestamp >= TIMESTAMP '2019-01-01' AND trip_start_timestamp < TIMESTAMP '2019-02-01'; -- expected: a new table with 31 day partitions, clustered by pickup_community_area; -- its Details tab shows the row count and size. Your numbers will differ.

Query it with and without the partition filter. Dry-run both first and compare the estimates. The first should fall to roughly one day's share of the three columns; the second should be refused outright.

★ Step 2 · sandbox queries (expected, your numbers will differ)-- A: with a partition filter, reads one day partition SELECT payment_type, COUNT(*) AS trips, ROUND(AVG(fare), 2) AS avg_fare FROM `YOUR_PROJECT.tw_lab.trips_jan2019` WHERE DATE(trip_start_timestamp) = '2019-01-15' AND pickup_community_area = 56 GROUP BY payment_type; -- B: no partition filter, refused because require_partition_filter is on SELECT payment_type, COUNT(*) AS trips FROM `YOUR_PROJECT.tw_lab.trips_jan2019` GROUP BY payment_type; -- expected: A runs, and its job details show the bytes processed and billed; -- B fails with an error asking for a filter on the partitioning column.

Check yourself

Three questions

Clear all three and builder session 3 gets stamped in your passport.

1 · What does require_partition_filter = TRUE do on a partitioned table?

It turns a forgotten partition filter into an error. The byte cap is a different setting, maximum_bytes_billed, from session 2.

2 · A table is clustered by (pickup_community_area, company). Which filter lets BigQuery skip the most blocks?

Rows are sorted by the first clustered column first, so its values sit together in few blocks. Values of the second column are scattered unless the first is also filtered.

3 · Why is the cluster rung, 36 of 257 blocks, labelled modelled when the partition rung is not?

The partition rung is exact: January 2019's 1,213,529 trips are an exact count. The cluster rung rests on a block model, and the dry run on a clustered table is only an upper bound.
