The bytes behind the bill

A BigQuery bill is not a mystery; it is arithmetic on a handful of documented rules. Tonight we do that arithmetic on one real public table, rung by rung, from a SELECT * that bills 77.03 GiB down to a query that bills the 10 MB floor. Then we price the alternative, a slot reservation, and finish with the four controls a leader can put in place, sorted by the one question that matters: does it tell you, or does it stop it?

Part 1 · covers on-demand bytes and the 10 MB minimum

Four rungs down one query

6 min live

On demand, BigQuery charges "$6.25 / 1 tebibyte" processed (us-central1, BigQuery pricing page, 3 November 2026), and "The first 1 TiB of query data processed per month is free." What counts as processed is the sum, over the columns a query references, of each value's logical size. So the levers are columns, then rows: name fewer columns, then let partitions and clusters skip the rows you did not ask for.

LiveWhat on-demand actually counts3 min▶

Logical bytes per value. BigQuery's data type sizes give 8 bytes for a number or timestamp, 2 plus the text's length for a string, and nothing for a NULL. Across all 23 columns the taxi table averages 390.7 logical bytes a row; taxi_id alone is 130.0, because it is a long string. That is how 211,670,894 rows become 77.03 GiB.

Only the columns referenced. "You're charged according to the total data processed in the columns you select". Three columns are 4.58 GiB of the 77.03.

LIMIT changes nothing. On-demand bills the bytes read "even if you set an explicit LIMIT"; Google's cost page puts it plainly: "applying a LIMIT clause to a query doesn't affect the amount of data that is read." SELECT * ... LIMIT 10 still bills 77.03 GiB.

The rounding rule. "Charges are rounded up to the nearest MB, with a minimum 10 MB data processed per table referenced by the query, and with a minimum 10 MB data processed per query." That is why the clustered rung reads 3.83 MB and bills 10.

What is free. "You aren't charged for queries that return an error or for queries that retrieve results from the cache."

Self-studyWhy the dry run is an upper bound on clustered tables2 min▶

A dry run asks BigQuery for a query's bytes before running it. On clustered tables it cannot be exact: Google's clustered tables page says "the number of blocks to scan isn't known until a query runs, you don't receive an accurate cost estimate before execution", and the estimate "is an upper bound".

The consequence shows up with the maximum bytes billed control in Part 3. That limit is checked against the estimate, so on a clustered table a query can fail even though the bytes it would actually have read were under the limit. Set the limit with headroom over the clustered rung, not tight against it. The bench's cluster rung (36 of 257 blocks read) is a model of BigQuery's block layout, not the real one, which Google does not publish.

Real world

The preview that read the whole table. An analyst exploring a new table types SELECT * ... LIMIT 10 to "just look at a few rows", many times a day, on the widest table in the warehouse. Each look bills every byte of every column. A query naming the three or four columns they cared about would have shown the same rows for a small fraction of the bytes. The story is a constructed composite; the LIMIT rule is Google's.

Part 2 · covers capacity: editions, slots, autoscaling, commitments

Paying for slots instead of bytes

5 min live

The other compute model buys capacity. A slot is a virtual CPU, and capacity is "measured in slots (virtual CPUs) over time". You choose an edition, set a reservation with a baseline that is always allocated, and let it autoscale above that. Then the bytes a query reads no longer change the bill; the hours your slots run do. For a workload that reads a great deal in predictable hours, that can be much cheaper.

LiveThe monthly comparison, and its assumption3 min▶

The bench's default: one dashboard query run 200 times a day for 30 days. On demand, SELECT * bills 451.32 TiB a month, $2,814.50 after the free TiB. The three-column version bills 26.85 TiB, $161.55. The partitioned rung bills 0.15 TiB and the clustered rung 0.06 TiB, both $0.00, inside the free TiB.

The capacity alternative: a 100-slot Standard reservation for 8 hours a day is 24,000 slot-hours a month at $0.04, $960.00; on Enterprise at $0.06 it is $1,440.00, or $1,152.00 at the 1-year price. The assumption, labelled because it is ours: the reservation is billed for the hours you set, and the queries fit inside those slots.

Self-studyEditions, autoscaling and commitments2 min▶

"BigQuery provides three editions": Standard, Enterprise and Enterprise Plus. "The baseline is the minimum number of slots that will always be allocated to the reservation", and above it "Slots always autoscale to a multiple of 50." Capacity "is billed per second with a one-minute minimum duration by default."

Two catches for a leader. First, Standard has "No access to BigQuery ML", so a team that plans models in SQL needs Enterprise or above. Second, commitments, the discount for promising capacity in advance, exist only on Enterprise and Enterprise Plus: "1-year commitment at 20% discount or 3-year commitment at 40% discount." That is where $0.048 and $0.036 come from.

One honest gap: the slot prices above come from the pricing page's default table, which lists us-central1 first. We could not verify the prices for the US multi-region, so do not assume they are identical; check the region picker on the pricing page for your own location.

Real world

The reservation bought to fix a query. Alarmed by an on-demand bill, a team buys a slot reservation sized for its busiest dashboard. The bill drops. Six months later someone rewrites the dashboard to name its columns, and finds it would have cost a small fraction of the reservation on demand. The capacity was a sensible purchase for the wrong problem. The story is a constructed composite; the arithmetic is the bench's.

Part 3 · covers storage, egress, and the controls that stop spend

Controls that tell you, and controls that stop it

4 min live

Most cost controls report. Few prevent. A leader needs to know which is which before an incident, because a report that arrives after the money is spent is a post-mortem, not a control. Google Cloud offers four that matter for BigQuery, and they sit at very different points on that line.

LiveThe four controls, in Google's words2 min▶

Budgets. "Setting an alerts-only budget doesn't automatically cap Google Cloud or Google Maps Platform usage or spending." A budget alert is a smoke detector, not a sprinkler.

Spend caps. New: "Spend caps are a cost control mechanism. A spend cap is enforced when usage costs exceed your budget target amount." They are "limited to budgets that are scoped to a single Google Cloud project and a single eligible service", and the eligible list is "Gemini API, Agent Platform (formerly known as Vertex AI), Cloud Run, and Cloud Run functions". BigQuery is not on it. "Any overage due to cost reporting latency is billed as usual." Secondary sources report the feature as Preview; the page we read does not say.

Custom quotas. QueryUsagePerDay caps a project, QueryUsagePerUserPerDay caps each user. The project default is "200 Tebibytes (TiB) of data processed per project per day". Hit the project quota and "BigQuery stops working for everyone in that project" until it resets, so a per-user quota is usually the kinder first line.

Maximum bytes billed. Set on a query: if the query would bill more, "the query fails without incurring a charge". It is the only one of the four that refuses the expensive query itself.

Self-studyStorage and network lines2 min▶

Storage is the quiet meter. In us-central1 (BigQuery pricing page, 3 November 2026), active logical storage is $0.000031507 per GiB-hour, "For 1 TiB for a full month, you pay $23.552"; long-term logical is $0.000021918. Physical storage is $0.000054795 active and $0.000027397 long-term, and time travel and fail-safe charges apply to physical storage. The first 10 GiB each month are free. Prices change: re-verify before you rely on them.

Moving data between regions has its own line: "Cross-region load jobs are billed for network usage under Network Data Transfer SKUs." For Tidewater, keeping the landing bucket and the BigQuery datasets in the same region, as session 1 suggested, keeps that line at zero for loads.

Real world

The budget alert that arrived after the money was spent. A team sets a monthly budget with alerts at 50%, 90% and 100%, and feels protected. Over a weekend a scheduled job with a bad join runs the same wide query again and again. The 100% email arrives on Monday morning, after the spend. Nothing failed: an alerts-only budget does exactly what its page says, and "doesn't automatically cap" spending. A maximum bytes billed on the job's queries would have stopped the first run. The story is a constructed composite.

Build-along

Tidewater's bill drill

★ 22 min · everyone builds

Paper only. tw-bi-prod is the constructed Tidewater project where the store managers' dashboards run. Assume its busiest dashboard behaves like the bench's taxi query. Write three controls for that project, a per-user quota, a maximum bytes billed on every query the dashboard runs, and a budget alert, each with where it is set and what it does; then write one sentence for the CFO. To try different numbers, move the levers on the bench in builder session 8.

Price the habit. From the ladder: the dashboard's wide query bills 77.03 GiB a run, the named-column version 4.58 GiB. At 200 runs a day that is $2,814.50 against $161.55 a month on demand (us-central1, BigQuery pricing page, 3 November 2026; re-verify).

Set the limit that stops it. Work the first row together. The limit must sit above the query you want and below the one you do not.

★ Worked example: maximum bytes billedControl: maximum bytes billed Where: each query the dashboard runs in tw-bi-prod (a per-query setting) Setting: 5 GiB per query (constructed: above 4.58 GiB, far below 77.03 GiB) Does: the three-column query runs; SELECT * fails "without incurring a charge" Watch: on clustered tables the estimate "is an upper bound", so leave headroom

Add the per-user quota and the budget alert. Choose a daily per-user cap with QueryUsagePerUserPerDay, so one person's mistake cannot exhaust the project for everyone. Then a budget with alerts for the project, written down honestly as "tells us", not "stops it".

Write the CFO sentence. One sentence, with the numbers, the control and what it does not cover.

★ The sentence, with the bench's numbersThe store dashboard would cost $2,814.50 a month reading every column; named columns bring it to $161.55, and day partitions bring it inside the free TiB. A 5 GiB per-query limit now refuses the wide version before it bills. Our budget alert reports; it does not stop spend. (BigQuery on-demand, us-central1, pricing page of 3 November 2026)

Do it for your own BI project. Find your widest dashboard query, its run count and its bytes. Write the same three rows. If you cannot fill "what it does" for a control, you do not yet know whether you have one.

✗ The cost plan that only reportsa budget alert at 100% and "we will react" a slot reservation bought before anyone looked at the query LIMIT 10 added to every dashboard query to "make it cheaper"

Sort every control into "tells you" or "stops it". In a cost review, write that label next to each control the team claims to have. A plan with only "tells you" controls is a reporting plan. It is useful, but it is not protection.

Three questions

Clear all three and leader session 5 gets stamped in your passport.

1 · An analyst adds LIMIT 10 to SELECT * on the 77.03 GiB taxi table. What does the query bill on demand?

Google: "applying a LIMIT clause to a query doesn't affect the amount of data that is read." The levers are columns, partitions and clusters, not LIMIT.

2 · Which control stops a runaway BigQuery query before it bills?

An alerts-only budget "doesn't automatically cap" spending, and BigQuery is not an eligible service for spend caps. Maximum bytes billed refuses the query itself.

3 · The clustered rung processes 3.83 MB but bills 10 MB. Why?

"Charges are rounded up to the nearest MB, with a minimum 10 MB data processed per table referenced by the query, and with a minimum 10 MB data processed per query." Below 10 MB, the floor decides.
