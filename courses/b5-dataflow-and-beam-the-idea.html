Dataflow and Beam, the idea

Dataflow is the Google Cloud service that runs Apache Beam pipelines. Before you spend a cent on workers, the idea fits on a laptop: a pipeline is a graph of steps, each step hands a collection to the next, and windows decide which events belong together in time. Tonight you write one Beam pipeline over the same 18,362 Chicago taxi trips as session 1, run it locally, and learn when the honest answer is "just write the SQL".

Where we start

Google's own one-line definition is the place to start: "Dataflow is a Google Cloud service that provides unified stream and batch data processing at scale", and "Dataflow executes Apache Beam pipelines" (Dataflow overview). So the skill you need first is Beam, not Dataflow. Beam ships a Direct Runner that "executes pipelines on your machine", which is how the build-along runs with no account and no bill. The same graph, given a different runner, goes to Dataflow; that step is shown on this page, not run, because it needs a billing-enabled project.

Part 1 · covers Pipeline, PCollection, PTransform

A pipeline is a graph you can read

5 min live

Beam asks you to describe the work, not to run it step by step. You build a graph: boxes are transforms, arrows are the collections that flow between them, and only when the graph is complete does a runner execute it, on your laptop or on Dataflow's workers. Three nouns from the Beam programming guide carry the whole model, and the build-along uses all three.

LiveThree nouns, straight from the Beam guide3 min▶

Pipeline. "A Pipeline encapsulates your entire data processing task, from start to finish." In the build-along it is the with beam.Pipeline(options=opts) as p: block; when the block closes, the runner executes the graph.

PCollection. "A PCollection represents a distributed data set that your Beam pipeline operates on." You never hold it in a Python list; you hand it to the next transform. trips in the script is a PCollection, and two branches read it.

PTransform. "A PTransform represents a data processing operation, or a step, in your pipeline." Every "Name" >> beam.Something(...) in the script is one, and the name in quotes is what you will see in a job graph later.

Self-studyParDo, GroupByKey and Combine, the three that do the work2 min▶

The guide names the core transforms. "ParDo is a Beam transform for generic parallel processing": one element in, zero or more out. beam.Filter and beam.Map in the script are the everyday element-by-element cases of that idea. "GroupByKey is a Beam transform for processing collections of key/value pairs": it gathers every value that shares a key. "Combine is a Beam transform for combining collections of elements or values in your data", and its per-key form combines the values for each key. Mean.PerKey is exactly that: the key is the year, the values are fares, and the result is one mean per year.

The professional habit: prefer a Combine to a GroupByKey followed by your own loop. A Combine tells the runner the operation can be done in parts and merged, which is what lets a runner spread it over many workers.

Real world

The pipeline Raj could draw on a whiteboard. At Tidewater Grocers (constructed), Raj from data-eng is asked whether loyalty scans can be cleaned before they land in sales_raw. Instead of a slide, he writes the Beam graph on a laptop with the Direct Runner, names every step, and shows the team the boxes and arrows. The review is about the graph, not about servers; the decision on where it runs comes later, in Part 3.

Part 2 · covers windows

Windows decide which events belong together

5 min live

A batch query groups by a column. A stream never ends, so "group by" needs a second question: over which stretch of time? Beam answers with windows, assigned by each element's event time, the moment the thing happened, not the moment the pipeline saw it. The build-along stamps every 2019 trip with its start time and counts trips in 30-day fixed windows.

LiveFour window types, in the guide's own words3 min▶

Fixed. "A fixed time window represents a consistent duration, non overlapping time interval in the data stream." Every element lands in exactly one window. Sliding. "sliding time windows can overlap", so one element can count in several windows: the shape for a moving 7-day total refreshed daily. Session. A session window "defines windows that contain elements that are within a certain gap duration of another element": a shopper's visit, closed by a quiet gap. Global. "all data in a PCollection is assigned to the single global window, and late data is discarded."

In the build-along, TimestampedValue gives each 2019 trip its start time as event time, and WindowInto(FixedWindows(30 * 24 * 3600)) cuts the year into 30-day windows. The counts come back as [300, 150, 150, 150, 150, 150, 150, 150, 150, 150, 149].

Self-studyReading the real counts, number by number2 min▶

The sample holds one 15-minute slot per month, and each slot carries about 150 trips. A 30-day window is shorter than most months, so the windows drift against the calendar, and once in the year two monthly slots fall inside the same window: that is the 300. Eleven windows hold data, twelve slots fed them.

The counts add up to 1,799, while session 1 found 1,800 rows in 2019. The difference is derived from the two outputs: the Has fare filter runs before the 2019 branch, so one 2019 trip with no fare never reached a window. That is the kind of off-by-one a graph makes easy to trace, because every step has a name.

Streaming design, late data, triggers and watermarks belong to learn-streaming-data; these pages stop at what the window types are and how Beam assigns them.

Real world

Same events, three different answers. Tidewater's loyalty lead, Lin, asks "how many visits did a member make last month?" (constructed). Fixed 30-day windows give one number per window; sliding windows give a fresh rolling number every day; session windows count visits, where a visit ends after a quiet gap. None of them is wrong. The window is a business definition, so agree it with Lin before the pipeline is written.

Part 3 · covers when Dataflow beats BigQuery SQL

When the graph earns its workers

5 min live

The mean fare per year in the build-along is one GROUP BY in BigQuery. Writing it in Beam is the right way to learn Beam and usually the wrong way to answer the question. The test is where the data already sits and what has to happen to it on the way: Dataflow earns its workers when the work is streaming, cut by event time, written in code SQL cannot express, or spread over sources that are not BigQuery tables.

LiveThe two-question test3 min▶

Is the data already in BigQuery, and does SQL say what you mean? Then stay in SQL. A scheduled query or a SQL step is cheaper to own: no workers, no job graph, and the bill is the bytes read, which sessions 2 and 3 taught you to shrink. Is it arriving as a stream, cut by event time, or crossing several systems? Then Beam on Dataflow is the tool built for it: Google's overview calls it "unified stream and batch data processing at scale", one graph for both.

There is a third option for teams that already write Spark: Managed Service for Apache Spark (formerly Dataproc), on clusters or serverless. Choosing among pipeline designs and orchestration is the job of learn-data-pipelines and learn-data-orchestration; these pages cover which Google Cloud service runs the result.

Self-studyWhat a Dataflow job puts on the bill2 min▶

The Dataflow pricing page lists the units: "Worker vCPU and memory (batch, streaming, and FlexRS)", "Dataflow Shuffle data processed (batch and FlexRS)", "Streaming Engine Compute Units or legacy Streaming Engine data processed (streaming only)" and "Data Compute Units (DCUs) (batch and streaming)". Also billed: "Persistent Disk, GPUs, and snapshots." And the clock: "Dataflow usage is billed in per second increments, on a per job basis."

The default table on that page showed, on 3 November 2026: vCPU $0.056 per hour, memory $0.003557 per GiB-hour, shuffle $0.011 per GiB processed. Our read did not name the region behind the default table, so treat these as one region's list prices, and re-verify them on the Dataflow pricing page for your region before you put them in a plan. The habit that matters more than the rate: a streaming job runs all month, so its workers bill all month, while a scheduled query bills only when it runs.

Real world

The streaming job that was a nightly GROUP BY. A team builds a Dataflow pipeline to total yesterday's sales per store, because "pipelines are Dataflow". It runs, it bills workers, and someone has to own the job graph. A year later a new engineer replaces it with one scheduled query over the same table. The story is a constructed composite; the lesson is to ask where the data sits before choosing the engine.

Build-along

A Beam pipeline on your laptop

★ 22 min · everyone builds

Five steps, one Python file, the session 1 sample. The pipeline reads three columns, computes the mean fare per year, and counts 2019 trips in 30-day windows. The output at the end is pasted from a real run of exactly this code, with apache-beam 2.77.0; the means are over the 18,362 sampled trips, not the City of Chicago's averages.

Reuse the environment from builder session 1 and add Beam. Activate the same .venv, in the folder that holds chicago_taxi_sample.parquet from session 1. If you skipped it, the curl line fetches the sample again. Beam is a large install; give it a minute.

★ Step 1 · setup (verified 3 November 2026, the session 1 environment). .venv/bin/activate pip install apache-beam==2.77.0 curl -O https://phoebefu6.github.io/learn-gcp-with-phoebe/data/chicago_taxi_sample.parquet

Choose the runner. runner="DirectRunner" keeps everything on your machine. The Direct Runner page says it plainly: it is for testing and development, and "not designed for production pipelines".

★ Step 2 · b5_beam.py, part 1# Builder session 5: an Apache Beam pipeline on the DirectRunner (your laptop), no Dataflow needed. # Needs: pip install apache-beam==2.77.0 import sys import apache_beam as beam from apache_beam.transforms.window import FixedWindows, TimestampedValue from apache_beam.options.pipeline_options import PipelineOptions SRC = sys.argv[1] if len(sys.argv) > 1 else "chicago_taxi_sample.parquet" opts = PipelineOptions(runner="DirectRunner")

Build the graph: read, filter, then the mean fare per year. trips is a PCollection read once and used by both branches. Mean.PerKey is the Combine; ToList gathers the eleven results so they print in year order.

★ Step 3 · b5_beam.py, part 2with beam.Pipeline(options=opts) as p: trips = (p | "Read" >> beam.io.ReadFromParquet(SRC, columns=["trip_start_timestamp", "payment_type", "fare"]) | "Has fare" >> beam.Filter(lambda r: r["fare"] is not None)) (trips | "Key by year" >> beam.Map(lambda r: (r["trip_start_timestamp"].year, r["fare"])) | "Mean per year" >> beam.combiners.Mean.PerKey() | "Sort" >> beam.combiners.ToList() | "Print years" >> beam.Map(lambda rows: [print(f"year {y} mean fare {m:6.2f}") for y, m in sorted(rows)]))

Add the second branch: event time and 30-day windows. This block stays indented inside the with. TimestampedValue sets each trip's event time; Count.Globally().without_defaults() counts per window and skips empty ones; the last three steps fold the windows back into one list to print.

★ Step 4 · b5_beam.py, part 3 (trips | "2019 only" >> beam.Filter(lambda r: r["trip_start_timestamp"].year == 2019) | "Event time" >> beam.Map(lambda r: TimestampedValue(r["payment_type"], r["trip_start_timestamp"].timestamp())) | "30-day windows" >> beam.WindowInto(FixedWindows(30 * 24 * 3600)) | "Count in window" >> beam.combiners.Count.Globally().without_defaults() | "Collect" >> beam.WindowInto(beam.window.GlobalWindows()) | "All windows" >> beam.combiners.ToList() | "Print windows" >> beam.Map(lambda ns: print("2019 trips per 30-day window:", sorted(ns, reverse=True))))

Run it and compare with this real output. Log lines omitted: Beam prints several WARNING and INFO lines around the result, and among them you will see Beam 2.77's DirectRunner start its local Prism runner and report "pipeline done!". Timings and ports vary by machine. The 2020 jump is 12 sampled 15-minute slots, not a finding about Chicago fares.

★ Step 5 · python b5_beam.py (real output, log lines omitted)year 2013 mean fare 11.29 year 2014 mean fare 12.52 year 2015 mean fare 12.93 year 2016 mean fare 13.86 year 2017 mean fare 13.09 year 2018 mean fare 15.11 year 2019 mean fare 13.40 year 2020 mean fare 22.74 year 2021 mean fare 18.93 year 2022 mean fare 20.80 year 2023 mean fare 22.26 2019 trips per 30-day window: [300, 150, 150, 150, 150, 150, 150, 150, 150, 150, 149]

On a billing-enabled project (optional). Shown, needs a billing-enabled project: the BigQuery sandbox covers BigQuery only, and the $300 Free Trial asks for a card. Check yourself

Three questions

Clear all three and builder session 5 gets stamped in your passport.

1 · In the build-along, what is trips?

You never loop over a PCollection yourself; you pass it to PTransforms. Both branches of the build-along read the same trips PCollection.

2 · You need a 7-day total refreshed every day, so one sale counts in seven windows. Which window type?

Fixed windows are "non overlapping", so each element lands in one. Session windows close on a gap. Only sliding windows overlap.

3 · The data is already in a BigQuery table and the job is a nightly total per store. Dataflow or SQL?

Dataflow earns its workers for streaming, event-time windows, logic SQL cannot express, or many sources and sinks. A batch total over a BigQuery table is a GROUP BY.
