Part 1 · covers the reference architecture (constructed)

From the till to the dashboard

5 min live

Tidewater's architecture is constructed, but every piece of it is a real Google Cloud service used the way its documentation describes. Sales files land in Cloud Storage with hive-style names. A Cloud Run function (formerly Cloud Functions) validates each file and loads it into BigQuery's sales_raw. Scheduled SQL, which uses "features of BigQuery Data Transfer Service", or a Dataflow job turns raw into sales_curated, partitioned by day and clustered by store area. Dashboards in a separate project read the curated table. Loyalty sign-ups arrive as events through Pub/Sub into the fenced loyalty_pii dataset.

LiveWalk the data once, naming the meter at every step3 min▶

Read the figure left to right and say the meter out loud at each box. The landing bucket bills bytes stored by class. The Cloud Run function bills requests and compute seconds. BigQuery bills sales_raw and sales_curated twice: bytes stored, and bytes read by every query. Dataflow, if Tidewater uses it, is "billed in per second increments, on a per job basis" for workers, memory and shuffle. The dashboards in tw-bi-prod read the curated table on every refresh, which is why session 5 put its biggest number on that arrow: a wide query 200 times a day bills 451.32 TiB a month on demand.

Notice what the separate BI project buys. Analysts get roles/bigquery.user in tw-bi-prod and read access on one dataset in tw-lake-prod, so their query jobs run from the BI project (a constructed design choice) and the data project's grants stay small.

Self-studyWhy loyalty arrives as events, and what that costs in design2 min▶

Sales come in daily files, so a function per file is enough. Loyalty sign-ups happen one at a time all day, so they arrive as Pub/Sub messages and a BigQuery subscription writes them into loyalty_pii. The design consequence is Google's default: "By default, Pub/Sub offers at-least-once delivery with no ordering guarantees", so the same sign-up can arrive twice and the curated view of members must de-duplicate. Pipeline design itself is taught in data pipelines and streaming in streaming data; these pages stop at which Google Cloud service carries which workload.

Real world

The diagram with no meters on it. A platform team presents a clean architecture diagram: logos, arrows, a lake and a warehouse. Asked what it will cost, they answer with the storage estimate. Nobody asks which arrow runs 200 times a day, and the dashboard arrow turns out to be the bill. The story is a constructed composite; adding one meter label per box is the whole fix.

Part 2 · covers governance: Knowledge Catalog, policy tags, row-level security

Fence the column, filter the row, catalogue the rest

5 min live

IAM decides who reaches a table. Inside the table, two more controls decide what they see. Column-level access control restricts columns with "policy tags", and it "is enforced in addition to existing dataset ACLs". Row-level security pairs a grantee list with a filter expression that "functions like a WHERE clause in a typical query". Above both sits Knowledge Catalog (formerly Dataplex Universal Catalog, renamed on 10 April 2026), which lets you "unify technical metadata and business semantics across structured and unstructured data".

LiveThree layers, three questions3 min▶

Can they reach the table? IAM, from session 3: a dataset grant, inherited down, with deny policies checked first. Tidewater's organization-level deny already keeps everyone except the privacy officers away from tables tagged pii = true. Which columns can they read? Policy tags. The member_email column carries one, and only principals with Fine-Grained Reader, role ID datacatalog.categoryFineGrainedReader, can read it, in addition to whatever dataset access they hold. Taxonomies "are regional resources, like BigQuery datasets and tables", so they live where the data lives. Which rows? A row access policy: a grantee list and a filter expression, so the Singapore analysts see Singapore members only.

The ideas behind these controls, role-based and attribute-based access, masking, access reviews, belong to data access control. A leader's job here is narrower: ask, for each sensitive column, which of the three layers fences it.

Self-studyWhat Knowledge Catalog adds, and what changed in the name2 min▶

Google's note on the rename: "As of April 10, 2026, Dataplex Universal Catalog is now called Knowledge Catalog. The API, client library, CLI, and IAM names remain unchanged." So scripts and roles still say dataplex; the analysts' Data Viewer role in builder session 4 includes several dataplex.* permissions for exactly that reason. The catalog's job for a leader is findability and early warning: its profiling scans check for "schema anomalies and statistical drift", which is how you learn that a source changed before the dashboard does. Older material describes Dataplex lakes, zones and assets; current documentation no longer does, so treat that model as legacy rather than designing around it.

Real world

The email column in every extract. A loyalty team shares member tables with three departments by granting dataset access, and each department exports what it needs. A year on, member emails sit in a dozen spreadsheets. A policy tag on one column would have let every department keep its access to points and tiers while the emails stayed behind one role. The story is a constructed composite.

Part 3 · covers ownership and the review questions

An owner and a control for every project

5 min live

A platform without owners is a platform where every incident starts with "whose is this?". Tidewater names one owner per project and one control on each meter. One caution from Google's budgets page decides how those controls are chosen: "Setting an alerts-only budget doesn't automatically cap Google Cloud or Google Maps Platform usage or spending." The newer spend-cap budgets work only for a single project and a single eligible service, and the eligible list, "Gemini API, Agent Platform (formerly known as Vertex AI), Cloud Run, and Cloud Run functions", does not include BigQuery. So BigQuery's real brakes are the ones session 5 taught: per-query ceilings and daily quotas.

LiveThe six questions, and why this order3 min▶

Which project comes first because it settles the next three by inheritance: the folder's policies, the billing account, the owner. Which location next, because it decides where the bytes physically sit, and cross-region loads are "billed for network usage under Network Data Transfer SKUs". Who pays: a billing account "defines who pays for a given set of Google Cloud resources". Which meter, and how often it runs: bytes read, slot-hours or compute seconds, times the refresh rate. Which deny protects the sensitive data, because allow policies only add. What ceiling stops one bad query: maximum_bytes_billed, under which "the query fails without incurring a charge", and the per-user daily quota.

A proposal that cannot answer one of these is not wrong, but it is not finished. Ask for the missing answer before asking about anything else.

Self-studyThe Well-Architected Framework, as a checklist behind the questions2 min▶

Google's Well-Architected Framework (the URL still says "architecture framework") has six pillars: "Operational excellence", "Security, privacy, and compliance", "Reliability", "Cost optimization", "Performance optimization" and "Sustainability". The six questions above lean on two of them, security and cost, because those are where data platforms most often go wrong first. Use the pillars as the longer checklist when a proposal passes the six questions and you want to look for what is missing: who is paged when the load fails, what happens if a region is lost, how fast the dashboard must be.

Self-studyThe Professional Data Engineer exam, and where these pages meet it3 min▶

Google's certification page lists the exam at 2 hours, "40 - 50 multiple choice and multiple select questions", and a $200 registration fee (certification page, 3 November 2026; re-verify before you book). Its exam guide has five sections, and these pages cover parts of each:

  • 1 · Designing data processing systems (~22%). Leader sessions 1, 3 and 6; builder session 4. Not taught: data migrations.
  • 2 · Ingesting and processing the data (~25%). Leader session 4; builder sessions 5 and 6. Not taught: Cloud Composer DAGs (Composer is "evolving to become Managed Service for Apache Airflow"), Datastream, change data capture.
  • 3 · Storing the data (~20%). Leader session 2; builder sessions 1, 2 and 3. Not taught: Bigtable, Spanner, AlloyDB, Cloud SQL.
  • 4 · Preparing and using data for analysis (~15%). Leader session 2; builder session 7. Not taught: Looker, BigQuery sharing (formerly Analytics Hub).
  • 5 · Maintaining and automating data workloads (~18%). Leader session 5; builder sessions 3 and 8. Not taught: monitoring and alerting in depth.

Also outside these pages: GKE, networking and VPC Service Controls beyond a mention, principal access boundary policies, custom-role authoring and BigQuery Omni. The official route is Google's learning path 16, "Professional Data Engineer Certification", on skills.google (formerly Cloud Skills Boost). Certificates and labs stay with Google; these pages are a way to understand the platform, not a substitute for the exam's own preparation.

Real world

The architecture review that asked only about services. A review board spends an hour on whether a new workload should use Dataflow or a managed Spark cluster, approves it, and moves on. Nobody asks which project it lands in. It lands in the analytics project, inherits the analysts' broad grants, bills to the wrong cost centre, and has no deny in front of the customer data it reads. Every one of those problems was one question away. The story is a constructed composite.

Ask "which project?" before "which service?", every time. It is the one question that settles inheritance, billing and ownership at once. Every other row on the page hangs from it.

Check yourself

Three questions

Clear all three and leader session 6 gets stamped in your passport.

1 · Tidewater puts a policy tag on member_email. What does it restrict?

Policy tags are column-level access control, "enforced in addition to existing dataset ACLs". Rows are the job of a row access policy.

2 · Which Tidewater control stops a contractor deleting production tables?

Deny policies attach to an organization, folder or project and are inherited downward. The contractors' grant is on the dev project anyway; the folder deny is the floor that holds even if someone later grants them more.

3 · A team proposes a new data workload. Which question do you ask first?

Service choice matters, but the project decides who pays, which policies already apply and who answers for it. Ask it first, then location, payer, meter, deny and ceiling.
